# A chapter release is its own upload session: pages are staged, then published by a commit that declares the whole order

A `Chapter Release` is created empty, pages are uploaded across as many requests as needed, and a commit declares the final ordered set. There is no session object: creating the release mints the id every later call addresses, uploads stage pages into it, and commit makes it readable -- a release is published iff it has at least one page carrying a `Sort Order`, so there is no publish flag, endpoint, or timestamp. The three steps: `POST /chapters/{chapter_id}/releases` (a plain resource constructor), `POST /releases/{release_id}/upload`, `POST /releases/{release_id}/commit` (RPC steps against an existing resource).

**Why the release is the session.** A separate upload-session table was rejected on the cost of committing it: a session stages objects under a session-scoped key, S3 has no rename, so promoting a committed session means copy-plus-delete per page -- a 200-page commit becomes 400 storage round-trips, no longer atomic. Making the release itself the session removes that: the release id exists before the first byte uploads, so the object key is final on upload and nothing moves. It also collapses editing into the same mechanism, since a session's real job for an edit -- holding references to existing pages for reuse -- is already served by reading the release's page list. Reader-facing atomicity holds: the ordinary page list carries committed pages only and a commit lands atomically, so a reader never sees a partly-uploaded set; a release opened before its first commit reports zero pages.

*Rejected: a single atomic multipart upload -- a second upload path beside the per-page one editing already requires, duplicating sniffing, size limit, and storage-then-database ordering (ADR-0005's argument for keeping covers out of book creation), and it puts a 200-page release in one unresumable request where a dropped connection at page 190 orphans everything.*

**Commit is the entire mutation surface** -- no `PUT`, `PATCH`, or per-page `DELETE`. Reordering and removing a page are a commit alone; inserting and replacing are an upload then a commit. A commit is a full declaration, so every row not named in it is deleted -- committed and merely-staged alike, with their objects -- making commit the reclamation mechanism for staged pages and keeping the row budget self-healing. Four positional mutation endpoints were specified and dropped: each needed its own shift logic, conflict handling, and tests to do what one declaration already does. Accepted cost: a one-page fix still declares every page, and replacing a page mints a new id (as ADR-0007 records for covers), acceptable because a page's reader-facing identity is its position, which is preserved.

**No `If-Match` precondition.** Commit is unconditional; no read carries an `ETag`. The concurrent-*commit* race is therefore unguarded: two clients read the same page list, A commits a declaration adding a page, B commits the list it read before A, deleting A's page and its object and answering `204` -- the lost update RFC 9110 s8.8.1 describes. This is mitigated, not closed, by limited release management: staging, commit, and delete are restricted to the release's `created_by` `User` or a `Moderator` (ADR-0003), so the racing parties are one owner across two devices, or an owner and a moderator -- not the whole `Uploader` population. The concurrent-*staging* race (below) is closed for the non-moderator case by the same restriction.

**The revision counter stays**, so adding an `If-Match`/`version` precondition later -- should the residual owner-vs-moderator window ever matter -- is additive. One statement -- `update chapter_releases set version = version + 1 where id = $1` -- opens the commit transaction, doubling as the increment and the row lock serialising concurrent commits; zero rows then means only that the release is missing, so the error path skips a separate existence probe. The release representation carries `version` as a plain read-only field, not a validator. Uploads don't bump it: it counts publications, not stages. *Rejected: a version-bump trigger -- `chapter_releases` has no other column a commit mutates, so a row trigger would need a dummy assignment to fire; a `chapter_pages` trigger would bump during staging; `xmin` never changes since a page edit doesn't touch the release row.*

**Uploads** are `multipart/form-data`, at most ten image parts per request (the transport ADR-0007 uses for covers, which allow one). Parts are consumed in order, field names ignored, leaving room for a named metadata part later. Each part streams and is abandoned the moment it passes 5 MiB, rather than buffered then measured, since a hostile part would otherwise sit fully resident before rejection. Format is sniffed from magic bytes, never the request; mixed formats within one release are allowed; stored content type comes from the sniff -- all as ADR-0007.

**Storage.** Pages live in their own bucket, so retention/quota policy can diverge from covers later; the object key is the page's bare uuid, computed and never stored, as for covers. *Rejected: a release-scoped key prefix -- enumerating a book's images through Postgres is one query, through storage it's one `ListObjectsV2` per release; the prefix made bulk teardown worse and diverged the batch-delete signature from the covers path for no payoff.* Storage-then-database ordering follows ADR-0005 (object written and confirmed before its row); deletion runs the other way, rows then objects, as for covers. Upload takes no transaction or lock -- a staged page has no position and so no ordering invariant; commit is the only transaction the feature adds.

**Deletion reclaims objects by making forgetting impossible.** `chapter_releases.chapter_id` is `on delete restrict` while `chapters.book_id` stays `on delete cascade` -- a `delete from books` fails loudly the moment it reaches a chapter with remaining releases (a `RESTRICT` on a grandchild blocks a cascade from a grandparent). Surfaced: `DELETE /chapters/{chapter_id}` and `DELETE /books/{book_id}` answer `409` while any release remains; the client clears them with `DELETE /releases/{release_id}` first, so a release delete -- not a chapter or book delete -- reclaims page objects, alongside commit reclaiming pages a declared order leaves out. *Rejected: deleting releases inside the chapter/book transaction -- it makes an unbounded object purge a side effect of a request naming none of it (one mistyped book id destroys every page beneath it), and a half-failed purge leaves exactly the rows-gone-objects-left orphaning the restrict prevents.*

**Reads.** No read hides an *unpublished* release: the `Chapter`'s release list returns every release with its page count, zero marking one still staged, and direct-id reads apply no publication filter -- ADR-0009's visibility gating still applies to both. Both release and page lists return whole with no pagination (ADR-0007's gallery exception to ADR-0002's cursor convention), since releases per chapter are bounded and a client about to reorder needs the whole page list. Staged pages are absent from the ordinary page list; `?status=Staged` on `GET /releases/{release_id}/pages` returns them instead. Page entries carry a relative link to the permanent per-page route, not a presigned URL, so a cached list never hands out expired links and the app never needs its own public origin.

Page *content* is gated per ADR-0009: while the owning `Book` is `Listed`, anyone; in any other state, a `Moderator+` or the `Chapter Release`'s own `created_by` -- not the `Book`'s `created_by`. Release and page *metadata* (the release row, its page count, the chapter's release list) follow ADR-0009's record tier instead -- open while the `Book` is `Listed` or `Hidden`, a `Moderator+` or the relevant `created_by` otherwise -- and cover-image reads follow that same record tier. The uncommitted-release exposure accepted above is metadata only and bounded by that tier, not open to the world.

**`GET /releases/{release_id}/pages/{page_number}`** is the permanent, bookmarkable route: it 302-redirects to a freshly presigned RustFS URL computed at request time (presigning is local HMAC signing, not a network round-trip). Chosen over full byte-proxying (avoids routing every page-view's bytes through the app on a self-hosted deployment) and over a bare presigned or unsigned URL handed to the client (a permanent reader link is a hard requirement a presigned URL's expiry can't meet). It needs no stored page count -- a nonexistent position doesn't match, and the miss is the 404. A sibling route `GET /releases/{release_id}/pages/{page_id}/image` addresses a page by id, letting a staged page (no position yet) be previewed before commit. Adding auth later is a change to the redirect handler, not a URL-scheme migration.

**Two costs accepted, not solved.** (1) Staged pages have no per-page owner. Release-level ownership (ADR-0003) keeps two plain `Uploader`s from ever sharing one release's staging area, so the destructive case narrows to an owner and a `Moderator` staging concurrently; `chapter_pages.uploaded_by` plus a caller-scoped commit deletion were weighed for that residual and left out. Read the staged list before committing. (2) A release never committed again holds its staged pages indefinitely -- reclamation is deferred alongside ADR-0005's orphaned-object sweep, though a stale staged page is a tracked row, making that sweep trivial.
