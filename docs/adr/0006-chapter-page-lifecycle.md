# A chapter release is its own upload session: pages are staged, then published by a commit that declares the whole order

A `Chapter Release` is created empty, pages are uploaded across as many requests as needed, and a commit declares the final ordered set. There is no session object: creating the release mints the id every later call addresses, uploads stage pages into it, and commit is what makes it readable -- a release is published iff it has at least one page carrying a `Sort Order`, so there is no publish flag, endpoint, or timestamp. The three steps are `POST /chapters/{chapter_id}/releases` (a plain resource constructor), `POST /releases/{release_id}/upload`, and `POST /releases/{release_id}/commit` (RPC steps against a resource that already exists).

**Why the release is the session.** A separate upload-session table was rejected on the cost of committing it: a session stages objects under a session-scoped key, S3 has no rename, so promoting a committed session means copy-plus-delete per page -- a 200-page commit becomes 400 storage round-trips, no longer atomic. Making the release itself the session removes that: the release id exists before the first byte uploads, so the object key is final on upload and nothing moves. It also collapses editing into the same mechanism, since a session's real job for an edit -- holding references to existing pages for reuse -- is already served by reading the release's page list. Reader-facing atomicity holds regardless: the ordinary page list carries committed pages only and a commit lands atomically, so a reader never sees a partly-uploaded set -- a release opened before its first commit reports zero pages.

*Rejected: a single atomic multipart upload -- it'd be a second upload path beside the per-page one editing already requires, duplicating sniffing, size limit, and storage-then-database ordering (the same argument ADR-0005 used to keep covers out of book creation), and it puts a 200-page release in one unresumable request where a dropped connection at page 190 orphans everything.*

**Commit is the entire mutation surface** -- no `PUT`, no `PATCH`, no per-page `DELETE`. Reordering and removing a page are a commit alone; inserting and replacing are an upload followed by a commit. A commit is a full declaration, so every row not named in it is deleted -- committed and merely-staged alike, with their objects -- making commit the reclamation mechanism for staged pages and keeping the row budget self-healing. Four positional mutation endpoints were originally specified and dropped: each needed its own shift logic, conflict handling, and tests to do what one declaration already does. Accepted cost: a one-page fix still declares every page, and replacing a page mints a new id (the same trade ADR-0007 records for covers), acceptable because a page's reader-facing identity is its position, and the position is preserved.

**The `If-Match` precondition was withdrawn before this work merged.** Commit had carried the release's revision as an `If-Match` precondition (RFC 9110 §13.1.1), answering `412` to a stale validator (§13.2.2) and `428` to an absent one (RFC 6585 §3). It was removed to hold the surface small until there's an identity to build the guard on. What it gave up is specific: it caught the concurrent-*commit* race -- two clients read the same page list, A commits a declaration adding a page, B then commits the list it read before A, deleting A's page and its object and answering `204` -- exactly the lost update RFC 9110 §8.8.1 describes, now unguarded. It never caught the concurrent-*staging* race (below), where both validators are current and the work is destroyed anyway -- only an ownership layer closes that. The withdrawal was accepted because both races close together once authentication lands, not because the first is harmless. Commit is now unconditional; `If-Match` is neither required nor read, and no read carries an `ETag`.

**The revision counter itself stays**, so reinstating the precondition is additive rather than a migration. One statement -- `update chapter_releases set version = version + 1 where id = $1` -- opens the commit transaction, doubling as the increment and the row lock serialising concurrent commits; zero rows now means only that the release is missing, so the error path skips a separate existence probe. The release representation carries revision as a plain read-only field, not a validator. Uploads deliberately don't bump it: it counts publications, not stages. *Rejected: a version-bump trigger -- `chapter_releases` has no other column a commit mutates (the existing `check_chapter_releases_language_not_publication` trigger fires only on immutable `language_id`), so a row trigger would need a dummy assignment to fire; a `chapter_pages` trigger would bump during staging; `xmin` never changes since a page edit doesn't touch the release row.*

**Uploads** are `multipart/form-data`, at most ten image parts per request -- the same transport ADR-0007 uses for covers, which allow one. Parts are consumed in order, field names ignored, leaving room for a named metadata part later without changing the transport. Each part streams and is abandoned the moment it passes 5 MiB, rather than buffered then measured, since a hostile part would otherwise sit fully resident before rejection. Format is sniffed from magic bytes, never taken from the request; mixed formats within one release are allowed; stored content type comes from the sniff -- all as ADR-0007 established.

**Storage.** Pages live in their own bucket, so retention/quota policy can diverge from covers later; the object key is the page's bare uuid, computed and never stored, exactly as for covers. *Rejected: a release-scoped key prefix -- enumerating a book's images through Postgres is one query, through storage it's one `ListObjectsV2` per release; the prefix made bulk teardown worse and diverged the batch-delete signature from the covers path for no payoff.* Storage-then-database ordering follows ADR-0005 (object written and confirmed before its row); deletion runs the other way, rows first then objects, matching cover deletion. Upload takes no transaction or lock -- a staged page has no position and so no ordering invariant; commit is the only transaction the feature adds.

**Deletion reclaims objects by making forgetting impossible.** `chapter_releases.chapter_id` is `on delete restrict` while `chapters.book_id` stays `on delete cascade` -- a `delete from books` fails loudly the moment it reaches a chapter with remaining releases (a `RESTRICT` on a grandchild does block a cascade from a grandparent). That refusal is surfaced: `DELETE /chapters/{chapter_id}` and `DELETE /books/{book_id}` answer `409` while any release remains; the client clears them with `DELETE /releases/{release_id}` first, so a release delete -- not a chapter or book delete -- reclaims page objects, alongside commit reclaiming pages a declared order leaves out. The already-shipped chapters foreign key needed no migration. *Rejected: deleting releases inside the chapter/book transaction -- it makes an unbounded object purge a side effect of a request naming none of it (one mistyped book id destroys every page beneath it), and a half-failed purge leaves exactly the rows-gone-objects-left orphaning the restrict exists to prevent.*

**Reads.** No read hides an unpublished release. The `Chapter`'s release list once filtered to published releases so a guest was never offered an empty one; that filter is withdrawn -- the list now returns every release with its page count, zero marking one still staged. Direct-id reads were never filtered. Both release and page lists return whole with no pagination, continuing ADR-0007's gallery exception to ADR-0002's cursor convention, since releases per chapter are bounded and a client about to reorder needs the whole page list. Staged pages are absent from the ordinary page list; `?status=Staged` on the same `GET /releases/{release_id}/pages` endpoint returns them instead. Page entries carry a relative link to the permanent per-page route rather than a presigned URL, so a cached list never hands out expired links and the application never has to know its own public origin. **(ADR-0009 supersedes the "unlisted, not secret" stance for page content: a `Moderator` or above, and the `Book`'s `created_by` user, may read pages in any book state; everyone else reads only `Listed` ones, and per-cover image reads are gated the same way. The draft-release exposure accepted here now holds for metadata only.)**

**`GET /releases/{release_id}/pages/{page_number}`** is the permanent, bookmarkable route: it 302-redirects to a freshly presigned RustFS URL computed at request time (presigning is local HMAC signing, not a network round-trip). Chosen over full byte-proxying (avoids routing every page-view's bytes through the app process on a self-hosted deployment) and over a bare presigned or unsigned URL handed to the client (a permanent reader link is a hard requirement a presigned URL's expiry can't satisfy). Wrapping the presign behind a stable app route gets both: the client's link never breaks and bytes are fetched directly from storage. It needs no stored page count -- a nonexistent position simply doesn't match, and the miss is the 404. A sibling route, `GET /releases/{release_id}/pages/{page_id}/image`, addresses a page by id, letting a staged page (no position yet) be previewed before commit.

Chapter pages have no auth gate today -- reads are anonymous per ADR-0003. Adding one later is a change to the redirect handler (check authorization, then presign-and-redirect or refuse), not a URL-scheme migration.

**Two costs are accepted rather than solved.** (1) Staged pages have no owner, so two uploaders staging into one release concurrently can destroy each other's uploads -- the losing commit is legitimate and races nothing the release row can observe (which is why the withdrawn precondition couldn't have caught it). The fix is the ownership layer dropped along with the session (one active session per account, staged files scoped to it), needing an identity that arrives with authentication: scope staged pages by uploader, narrow commit's deletion to the caller's own rows. Until then, the mitigation is reading the staged list before committing. (2) A release never committed again holds its staged pages indefinitely -- reclamation is deferred alongside ADR-0005's orphaned-object sweep, though a stale staged page is a tracked row, making that sweep trivial to write when it comes.
