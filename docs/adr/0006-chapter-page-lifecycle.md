# A chapter release is its own upload session: pages are staged, then published by a commit that declares the whole order

A `Chapter Release` is created empty, pages are uploaded into it across as many requests as needed, and a commit declares the final ordered set. There's no session object: creating the release mints the id every later call addresses, uploads stage pages into it, and commit is what makes it readable -- a release is published iff it has at least one page carrying a `Sort Order`, so there's no publish flag, endpoint, or timestamp. The three steps are `POST /chapters/{chapter_id}/releases`, `POST /releases/{release_id}/upload`, `POST /releases/{release_id}/commit`; creation is a plain resource constructor, the other two are RPC steps against a resource that already exists.

A separate upload-session table was the starting point, rejected on the cost of committing it: a session stages objects under a session-scoped key, and S3 has no rename, so promoting a committed session means a copy-plus-delete per page -- a 200-page commit becomes 400 storage round-trips, no longer fast or obviously atomic. Making the release itself the session removes that: the release id exists before the first byte uploads, so the object key is final on upload and nothing moves. It also collapses editing into the same mechanism, since a session's real job for an edit -- holding references to existing pages for reuse -- is already served by reading the release's page list. Reader-facing atomicity holds regardless: the ordinary page list carries committed pages only and a commit lands atomically, so a reader never sees a partly-uploaded set -- a release opened before its first commit just reports zero pages.

A single atomic multipart upload was the original spec, rejected for the opposite reason: it'd be a second upload path beside the per-page one editing already requires, duplicating sniffing, size limit, and storage-then-database ordering -- the same argument ADR-0005 used to keep covers out of book creation. It also puts a 200-page release in one unresumable request, where a dropped connection at page 190 orphans everything and the client starts over.

Commit is the entire mutation surface -- no `PUT`, no `PATCH`, no per-page `DELETE`. Reordering and removing a page are a commit alone; inserting and replacing are an upload followed by a commit. A commit is a full declaration, so every row not named in it is deleted -- committed and merely-staged alike, with their objects -- making commit the reclamation mechanism for staged pages and keeping the row budget self-healing. Four positional mutation endpoints were originally specified and dropped: each needed its own shift logic, conflict handling, and tests to do what one declaration already does. The accepted cost: a one-page fix still declares every page, and replacing a page mints a new id -- the same trade ADR-0007 records for covers, acceptable here for the same reason, since a page's reader-facing identity is its position, and the position is preserved.

That cost was originally guarded by a precondition, since withdrawn. Commit carried the release's revision as an `If-Match` precondition (RFC 9110 §13.1.1), answering `412` to a stale validator (§13.2.2) and `428` to an absent one (RFC 6585 §3). It was removed before this work merged, to hold the surface small until there's an identity to build the guard on -- and what that gives up is specific, not nothing. The precondition caught the concurrent-*commit* race: two clients read the same page list, A commits a declaration adding a page, B then commits the list it read before A -- deleting A's page and its object, answering `204`. That's exactly the lost update RFC 9110 §8.8.1 describes, and it's now unguarded. What the precondition never caught is the concurrent-*staging* race (below), where both validators are current and the work is destroyed anyway -- only an ownership layer closes that one. The withdrawal was accepted because both races close together once authentication lands, not because the first is harmless. Commit is therefore unconditional, `If-Match` neither required nor read, no read carries an `ETag`. It returns alongside the per-uploader scoping this document already defers to.

The revision counter itself stays, since it's what makes reinstating the precondition additive rather than a migration. One statement -- `update chapter_releases set version = version + 1 where id = $1` -- opens the commit transaction, doubling as the increment and the row lock serialising concurrent commits; zero rows now means only that the release is missing, so the error path skips a separate existence probe. The release representation carries revision as a plain read-only field, not a validator. Uploads deliberately don't bump it: it counts publications, not stages. A version-bump trigger was considered and rejected -- `chapter_releases` has no other column a commit mutates (the existing `check_chapter_releases_language_not_publication` trigger fires only on immutable `language_id`), so a row trigger would need a dummy assignment to fire at all; a `chapter_pages` trigger would bump during staging; and `xmin` never changes since a page edit doesn't touch the release row.

Uploads are `multipart/form-data`, at most ten image parts per request -- the same transport ADR-0007 uses for covers, differing only in part count: one there, up to ten here. Parts are consumed in order, field names ignored, leaving room for a named metadata part later without changing the transport. Each part streams and is abandoned the moment it passes 5 MiB, rather than buffered then measured, since the body limit governs the whole request and a hostile part would otherwise sit fully resident before rejection. Format is sniffed from magic bytes, never taken from the request; mixed formats within one release are allowed; stored content type comes from the sniff -- all as ADR-0007 established for covers.

Pages live in their own bucket, so retention/quota policy can diverge from covers later; the object key is the page's bare uuid, computed and never stored, exactly as for covers. A release-scoped key prefix was designed and rejected on measurement, not taste: enumerating a book's images through Postgres is one query, through storage it's one `ListObjectsV2` per release -- the prefix made bulk teardown worse, and diverged the batch-delete signature from the covers path for an ops convenience that didn't pay off. Storage-then-database ordering follows ADR-0005 unchanged (object written and confirmed before its row); deletion runs the other way, rows first then objects, matching cover deletion. Upload takes no transaction or lock -- a staged page has no position and so no ordering invariant; commit is the only transaction the feature adds.

Deleting a release, `Chapter`, or `Book` must reclaim objects, so the schema makes forgetting impossible rather than merely discouraged. `chapter_releases.chapter_id` is `on delete restrict` while `chapters.book_id` stays `on delete cascade` -- verified that a `delete from books` fails loudly the moment it reaches a chapter with remaining releases (a `RESTRICT` on a grandchild does block a cascade from a grandparent). That refusal is surfaced, not worked around: `DELETE /chapters/{chapter_id}` and `DELETE /books/{book_id}` answer `409` while any release remains; the client clears them with `DELETE /releases/{release_id}` first, so a release delete -- not a chapter or book delete -- is what reclaims page objects, alongside commit reclaiming pages a declared order leaves out. The already-shipped chapters foreign key needed no migration. Deleting releases inside the chapter/book transaction was rejected: it makes an unbounded object purge a side effect of a request naming none of it -- one mistyped book id destroys every page beneath it, and a half-failed purge leaves exactly the rows-gone-objects-left orphaning the restrict exists to prevent. Under an all-cascade schema, the same forgotten path would silently orphan every image under the book.

No read hides an unpublished release. The `Chapter`'s release list once filtered to published releases (at least one committed page), so a guest was never offered an empty one; that filter is withdrawn, and the list now returns every release with its page count, zero marking one still staged. Direct-id reads were never filtered -- a draft was unlisted, not secret, and with no auth in the API nothing could make it secret anyway -- the list now shows drafts too. Both release and page lists return whole with no pagination, continuing ADR-0007's gallery exception to ADR-0002's cursor convention, since releases per chapter are bounded and a client about to reorder needs the whole page list regardless. Staged pages are absent from the ordinary page list; `?status=Staged` on the same `GET /releases/{release_id}/pages` endpoint returns them instead. Page entries carry a relative link to the permanent per-page route rather than a presigned URL, so a cached list never hands out expired links, and the application never has to know its own public origin.

`GET /releases/{release_id}/pages/{page_number}` is that permanent, bookmarkable route: it 302-redirects to a freshly presigned RustFS URL computed at request time (presigning is local HMAC signing, not a network round-trip). Chosen over full byte-proxying, to avoid routing every page-view's bytes through the app process on a self-hosted deployment. Chosen over a public/unsigned bucket URL or a bare presigned URL handed directly to the client, because a permanent reader link ("live forever until deleted explicitly") is a hard requirement a bare presigned URL can't satisfy -- its whole security property is the expiry. Wrapping the presign behind a stable app route gets both: the client's link never breaks, and bytes are fetched directly from storage with no app bandwidth cost, since each redirect target is signed fresh. It needs no stored page count to bound itself -- a nonexistent position simply doesn't match, and the lookup miss is the 404. A sibling route, `GET /releases/{release_id}/pages/{page_id}/image`, addresses a page by id, letting a staged page (no position yet) be previewed before commit.

Chapter pages have no auth gate today -- reads are anonymous per ADR-0003. Adding one later is a change to the redirect handler (check authorization, then presign-and-redirect or refuse), not a URL-scheme migration.

Two costs are accepted rather than solved. Staged pages have no owner, so two uploaders staging into one release concurrently can destroy each other's uploads -- the losing commit is legitimate and races nothing the release row can observe, which is why the withdrawn precondition couldn't have caught it either. What would prevent it is the ownership layer dropped along with the session (one active session per account, staged files scoped to it), and that needs an identity that doesn't exist until authentication lands; the fix is scoping staged pages by uploader and narrowing commit's deletion to the caller's own rows. Until then, the mitigation is reading the staged list before committing. Separately, a release never committed again holds its staged pages indefinitely -- reclaiming them is deferred alongside the orphaned-object reconciliation ADR-0005 already defers, though unlike a true orphan a stale staged page is a tracked row, making that sweep trivial to write when it comes.
