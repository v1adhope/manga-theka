# A chapter release is its own upload session: pages are staged, then published by a commit that declares the whole order

A `Chapter Release` is created empty, its pages are uploaded into it across as many requests as the client needs, and a commit then declares the final ordered set. There is no session object. Creating the release mints the id that every later call addresses, uploads stage pages into it, and the commit is what makes the release readable -- a release is published if and only if it has at least one page carrying a `Sort Order`, so there is no publish flag, no publish endpoint, and no publication timestamp. The three steps are `POST /chapters/{chapter_id}/releases`, `POST /releases/{release_id}/upload`, and `POST /releases/{release_id}/commit`; creation is a plain resource constructor while the other two are RPC, because they are steps against a resource that already exists.

A separate upload-session table was the starting point and was rejected on the cost of committing it. A session has to stage its objects under a session-scoped key, and S3 has no rename, so promoting a committed session means a copy plus a delete for every page -- a 200-page commit becomes 400 storage round-trips and stops being either fast or obviously atomic. Making the release itself the session removes that entirely: the release id exists before the first byte is uploaded, so the object key is final on upload and nothing ever moves. It also collapses editing into the same mechanism, since a session's real job for an edit -- holding references to the existing pages so the client can reuse them -- is already served by reading the release's page list. The atomicity a reader cares about is preserved regardless: no reader ever sees a partly-uploaded release, because an uncommitted one is unlisted.

A single atomic multipart upload was the originally specified shape and was rejected for the opposite reason. It would have been a second upload path beside the per-page one that has to exist anyway for editing, duplicating the sniffing, the size limit, and the storage-then-database ordering -- the same argument ADR-0005 used to keep covers out of book creation. It also put a 200-page release in one unresumable request, where a dropped connection at page 190 orphans everything and the client starts over.

Commit is the entire mutation surface. There is no `PUT`, no `PATCH`, and no per-page `DELETE`; reordering and removing a page are a commit alone, while inserting and replacing are an upload followed by a commit. A commit is a full declaration, so every row of the release not named in it is deleted -- pages previously committed and pages merely staged alike, with their objects -- which also makes commit the reclamation mechanism for staged pages and keeps the per-release row budget self-healing. Four positional mutation endpoints were specified originally and dropped: each would have needed its own shift logic, its own conflict handling, and its own tests, to do what one declaration already does. The accepted cost is that a one-page fix still declares every page in the release, and that replacing a page mints a new page id -- the same trade ADR-0007 records for covers, and acceptable here for the same reason, because a page's reader-facing identity is its position and the position is preserved.

That cost is exactly why the declaration is guarded. Commit carries the release's revision as an `If-Match` precondition per RFC 9110 section 13.1.1, answering `412` to a stale validator per section 13.2.2 and `428` to an absent one per RFC 6585 section 3; without it, two clients each declaring a whole page order would silently overwrite each other, which is the lost-update problem section 8.8.1 describes. The revision belongs to the database. One statement -- `update chapter_releases set version = version + 1 where id = $1 and version = $2` -- opens the commit transaction and is simultaneously the precondition check, the increment, and the row lock that serialises concurrent commits; zero rows means stale or missing, and only that error path pays an existence probe to tell `412` from `404`. Uploads deliberately do not bump it, so a client's own staging cannot invalidate the validator it is about to commit with. A trigger was considered and rejected: `chapter_releases` has no other mutable column, so a row trigger needs a dummy assignment to fire at all and guards an empty set, a trigger on `chapter_pages` fires once per row and would bump during staging, and `xmin` never changes at all because a page edit does not touch the release row.

Uploads are `multipart/form-data`, at most ten image parts per request, which is a scoped exception to ADR-0007's "raw request body, not multipart" rule rather than a contradiction of it -- that reasoning turned on a cover being exactly one image with no accompanying fields, and a page batch is neither. Parts are consumed in order and their field names ignored, which leaves room for a named metadata part later without changing the transport. Each part is streamed and abandoned the moment it passes 5 MiB rather than buffered and then measured, because the body limit governs the whole request and a single hostile part would otherwise be fully resident before it could be rejected, once per concurrent uploader. Format is sniffed from magic bytes and never taken from the request, mixed formats within one release are allowed, and the object's stored content type comes from the sniff -- all as ADR-0007 established for covers.

Pages live in a bucket of their own, so retention and quota policy can diverge from covers later, and the object key is the page's bare uuid, computed and never stored, exactly as for covers. A release-scoped key prefix was designed and rejected on measurement rather than taste: enumerating a book's images through Postgres is one query, while enumerating through storage is one `ListObjectsV2` per release, so the prefix made bulk teardown worse rather than better, and it would have diverged the batch-delete signature from the covers path to buy an ops convenience. Storage-then-database ordering follows ADR-0005 unchanged -- the object is written and confirmed before its row is inserted, so a failure orphans an object rather than leaving a row addressing nothing -- and deletion runs the other way, rows first and then objects, matching the existing cover deletion. Upload takes no transaction and no lock at all, because a staged page has no position and therefore participates in no ordering invariant; commit is the only transaction the feature adds.

Deleting a release, a `Chapter`, or a `Book` must reclaim objects, and the schema is arranged so that forgetting is impossible rather than merely discouraged. `chapter_releases.chapter_id` is `on delete restrict` while `chapters.book_id` stays `on delete cascade`, which was verified to mean that a `delete from books` fails loudly the moment it reaches a chapter that still has releases -- a `RESTRICT` on a grandchild does block a cascade arriving from a grandparent. That refusal is surfaced rather than worked around: `DELETE /chapters/{chapter_id}` and `DELETE /books/{book_id}` answer `409` while any release remains, and the client clears them with `DELETE /releases/{release_id}` first, so a release delete rather than a chapter or book delete is what reclaims page objects -- alongside commit, which reclaims the pages a declared order leaves out. The already-shipped chapters foreign key needed no migration. Deleting the releases inside the chapter or book transaction was rejected: it makes an unbounded object purge a side effect of a request naming none of it, so one mistyped book id destroys every page beneath it, and a purge that half-fails leaves exactly the rows-gone-objects-left orphaning the restrict exists to prevent. Under an all-cascade schema the same forgotten path would silently orphan every image under the book.

Only one read hides an unpublished release: the `Chapter`'s release list. Everything reachable by direct id stays reachable, so an uploader can inspect a release before committing it -- a draft is unlisted, not secret, and with no authentication in the API there is no mechanism that could make it secret anyway. Both the release list and the page list are returned whole with no pagination, continuing ADR-0007's gallery exception to ADR-0002's cursor convention, since releases per chapter are bounded by how many groups translate one chapter and a client about to reorder needs the entire page list regardless. Staged pages are absent from the ordinary page list and have a management read of their own, which deliberately carries no `ETag` because staging changes that representation without bumping the revision. Page entries carry a relative link to the permanent per-page route rather than a presigned URL, so a cached list never hands out expired links and the application never has to know its own public origin.

`GET /releases/{release_id}/pages/{page_number}` is that permanent, bookmarkable route: it 302-redirects to a freshly presigned RustFS URL computed at request time -- presigning is local HMAC signing against the storage access key, not a network round-trip to RustFS -- rather than either streaming image bytes through the app or exposing a public/unsigned bucket URL. This was chosen over full byte-proxying to avoid routing every page-view's image bytes through the app process on a self-hosted deployment. It was chosen over a public/unsigned bucket URL, or a bare presigned URL handed to the client directly, because a permanent reader link was a hard requirement ("live forever until deleted explicitly") that a bare presigned URL can't satisfy on its own -- its whole security property is the expiry. Wrapping the presign behind a stable app route gets both: the link the client holds never breaks, while the actual bytes are fetched directly from storage with no app bandwidth cost, since each redirect target is signed fresh. It needs no stored page count to bound itself -- a position that does not exist simply does not match, and the lookup miss is the 404. A sibling route addresses a page by id instead, which is what lets a staged page, having no position at all, be previewed before it is committed.

Chapter pages have no auth gate today -- reads are anonymous per ADR-0003. This shape means adding one later is a change to the redirect handler (check authorization, then presign-and-redirect or refuse), not a URL-scheme migration.

Two costs are accepted rather than solved. Staged pages have no owner, so two uploaders staging into one release concurrently can destroy each other's uploads: the losing commit is legitimate and its validator was never stale, so the precondition cannot catch it. What would prevent it is the ownership layer this design dropped along with the session -- one active session per account, with staged files scoped to that session -- and that needs an identity which does not exist until authentication lands. The fix then is to scope staged pages by uploader and narrow commit's deletion to the caller's own rows, restoring the ownership layer without restoring the session. Until then the mitigation is reading the staged list before committing. Separately, a release that is never committed again holds its staged pages indefinitely, so reclaiming them is deferred alongside the orphaned-object reconciliation ADR-0005 already defers -- though unlike a true orphan a stale staged page is a tracked row, which makes that sweep trivial to write when it comes.
