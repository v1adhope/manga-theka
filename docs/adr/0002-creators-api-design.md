# Creators API: plural REST with `{data}` envelope and UUID-v7 cursor pagination

The creators API uses plural REST routes (`/creators`, `/creators/{id}`) with a uniform `{data: ...}` envelope across all endpoints, including `POST /creators` (migrated from the singular `/creator` path with a bare `{id}` body). Wrapping in `{data}` lets single-item, list, and create-acknowledgement responses share one shape; `nextCursor` is always present (no `skip_serializing_if`) and `null` at end of list.

List pagination is cursor-based on the raw UUID v7 id (`?after=<uuid>&limit=<n>`, `WHERE id < $after ORDER BY id DESC`), over-fetching by one row to detect the next page in a single query. The v7 id encodes creation time, so ordering by id equals ordering by `created_at` with no ties possible -- a separate `created_at` cursor would be redundant. Opaque/base64 cursors were rejected for raw UUIDs, favoring debuggability while no client depends on the wire format yet.

Validation splits by failure level: syntax/parse errors (malformed UUID, non-integer limit) return 400 via axum's default rejection; semantic violations (limit out of `[1, 100]`, name not letters-only) return 422; a duplicate full name returns 409 per RFC 9110 §15.5.10, which scopes 409 to conflicts with the target resource's current state and reserves 422 for content-shape violations. PUT and DELETE detect missing rows via a `RETURNING id` clause (one round-trip), mapping `None` to `DatabaseError::not_found::<Creator>()` → 404 with a plain-text `"Creator not found"` body, matching the existing `DatabaseError` convention. PUT keeps `created_at` immutable by omitting it from the `UPDATE` SET clause; the route builds the `Creator` value with a `UNIX_EPOCH` placeholder for that field, preserving the non-`Option` entity invariant. Timestamps serialize as RFC 3339 via `time::serde::rfc3339` directly on `Creator` (no separate DTO); `Name` serializes as its inner string via `#[serde(transparent)]`; `Uuid` stays typed. `Creator` carries no `role` -- it's a person's identity only (`id`, `first_name`, `last_name`, `created_at`). `CreatorRole` lives on the book-credit relation (`book_creators`, see ADR-0005), since the same person is routinely credited as both Artist and Author.
