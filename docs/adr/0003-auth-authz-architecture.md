# Authentication and authorization: dual JWT (access + refresh) with per-session Redis session store

The authentication system introduces a `User` aggregate (distinct from `Creator`), each holding a set of roles (`Reader`, `Uploader`, `Moderator`, `Admin`) as `text[]` with a CHECK constraint (`cardinality(roles) > 0`, each element in the four-role set). Reads are anonymous; writes are gated by an OR role-gate applied per-route via a `from_fn_with_state` middleware injecting `AuthenticatedUser { id, sid, roles }` into request extensions. `POST /sessions` (login) issues two Ed25519-signed JWT classes: a stateless 15-min access JWT (`typ: "at+jwt"`, claims `sub`/`sid`/`role`/`iat`/`exp`) in the JSON body for in-memory JS storage, and a 30-day refresh JWT (`typ: "rt+jwt"`, claims `sub`/`sid`/`jti`/`iat`/`exp`) in an `HttpOnly; Secure; SameSite=Strict; Path=/sessions; Max-Age=2592000` cookie. Signing keypairs are per-class, loaded from `APP_JWT_ACCESS__KEY`/`APP_JWT_REFRESH__KEY` as file paths to raw 32-byte Ed25519 seeds, public key derived in-memory at startup. `typ` (RFC 9068 `at+jwt` plus the project's analogous `rt+jwt`) at the JOSE-header level prevents token-class confusion; `alg` is pinned server-side to `EdDSA`, `none` rejected.

Refresh tokens live in two Redis structures per user: a SET `sids:<sub>` listing active session ids, and per-session STRING keys `refresh-tokens:<sub>:<sid>` holding `{"jti": "<KeyedBLAKE3(jti)>", "ua", "ip", "createdAt", "updatedAt"}` with a native TTL of the refresh-token lifetime (30 d). `createdAt` is set at login and never mutated; `updatedAt` bumps on each refresh. `POST /sessions/refresh` extracts `sub`/`sid`/`jti` from the verified JWT, `GET`s the session JSON, compares `keyed_blake3(jti)` to the stored value, and on match issues a new refresh JWT with a fresh `jti`, then pipelines `SET ... EX 2592000` + `SADD sids:<sub> <sid>` (idempotent) + `EXPIRE sids:<sub> 2592000` in one atomic `MULTI`/`EXEC`; on mismatch it `tracing::warn!`s and returns 401 -- no reuse-detection or family-revocation escalation, just the log signal. `DELETE /sessions/all` deletes every key from `SMEMBERS sids:<sub>` plus `DEL sids:<sub>`. `DELETE /sessions/me/current` logs the requester out via the JWT's own sid (no path sid), bypassing the 24h rule so a freshly-logged-in user can always self-logout. `DELETE /sessions/me/{sid}` revokes one of the requester's other sessions, ownership-checked via `SISMEMBER sids:<sub> <sid>`. The 24h-revoke-protection rule covers both: if the requester's session `createdAt` is under 24h old, the request is `409` -- an attacker who just compromised credentials can't immediately lock out the user's other sessions. `GET /sessions/me` reads `SMEMBERS sids:<sub>` then `MGET`s the per-session keys, returning only the still-alive pairs and lazily `SREM`-ing the rest (native TTL can clear a key before the SET catches up, so the SET is a superset filtered on read). `POST /sessions` (login) uses the same pipelined write as refresh. The Redis client is `redis` with `ConnectionManager` (auto-reconnecting, multiplexed); BLAKE3 is keyed with an env pepper (`APP_BLAKE3__KEY`), distinct from the JWT signing keys.

Passwords are hashed with Argon2id (`argon2` crate), params from `APP_PASSWORD__M_COST`/`__T_COST`/`__P_COST` via `envious`+`serde`, stored as the PHC string in a single `password_hash TEXT` column (per-user salt embedded, no pepper). Policy is length 16-128, no composition rules (NIST SP 800-63B). Registration (`POST /users`) is open for the default `{Reader}` role. Moderator and Admin share the content-moderation gate (`require_roles([Moderator, Admin])`); Admin alone gates user-promotion (`require_roles([Admin])`) -- the privilege gap is enforced by routing, not role hierarchy. Moderator may grant/revoke `Uploader` for other Users; Admin may grant/revoke any role, via `array_append`/`array_remove` on `users.roles` (promotion endpoint deferred from v1). Login identifier is email (`POST /sessions` takes `email` despite `username` also being unique); `Email` and `Username` are newtypes with `TryFrom<String>` validation in the entity layer -- `Email` via `validator::validate_email`, `Username` via `^[a-zA-Z0-9_]{3,32}$` (no `validator` derive macros, mirroring `Name`). Email verification is deferred for v1, but `verified_at timestamptz null` is reserved on `users`.

Routes follow plural REST (ADR-0002) with `{data}` envelope. `/users`: `POST /users` (register, anonymous), `GET /users/me` (current user). `/sessions`: `POST /sessions` (login, anonymous-via-credentials), `POST /sessions/refresh` (refresh-cookie; the one action sub-resource -- a pragmatic breach of pure REST), `DELETE /sessions/all` (logout-all, payload from JWT, gated by the 24h rule), `DELETE /sessions/me/current` (self-logout via JWT sid, no path sid, exempt from the 24h rule), `DELETE /sessions/me/{sid}` (revoke one other own session, gated by the 24h rule), `GET /sessions/me` (list own sessions as `sid`/`ua`/`ip`/`createdAt`/`updatedAt`, `jti` scrubbed). `me`, `current`, `all`, `refresh` are reserved path aliases and must register before the `{sid}` pattern in the router. Error map: 400 parse / 401 unauthenticated / 403 role-gate fail / 404 `sub` deleted on `/users/me` / 409 duplicate email-or-username on `POST /users` or 24h-revoke-protection block / 422 semantic / 500 internal; 401 reveals only "Invalid credentials", 403 only "Forbidden". The 409 for duplicate email-or-username matches ADR-0002's RFC 9110 §15.5.10 reading for duplicate creator names: a state conflict is 409, content-shape violations (regex miss, out-of-range length) are 422. New deps: `argon2`, `jsonwebtoken`, `blake3`, `redis` (`tokio-comp`), `validator`, `regex`; `secrecy` was already present for env secret wrapping.

Rejected: the `/auth/*` action namespace (RFC 6749-style), for plural resources under `/users`/`/sessions` consistent with ADR-0002. Rejected: stateful access tokens (whitelist/denylist per-token), preserving the handoff's "CPU-only, zero DB queries on protected requests" property at the cost of an up-to-15-min window where a logged-out user's access JWT keeps working (mitigated by short TTL). Rejected: a per-user HASH model, for per-session STRING keys with native Redis TTL -- expiry then lives with the data it governs, rather than split between HASH-level TTL and handler-side `expires_at` checks; the `sids:<sub>` SET stays as a lookup index so `GET /sessions/me` and `DELETE /sessions/all` use `SMEMBERS`+`MGET` instead of a keyspace SCAN (O(keyspace) per request, unusable around ~100k keys). Rejected: reuse-detection state (`previous_jti` or a used-jti SET) -- simpler session JSON, at the cost of a breach alarm the warn-log replaces. Rejected: `citext` for email, keeping canonicalisation at the entity layer.
