# Authentication and authorization: dual JWT (access + refresh) with per-session Redis session store

The authentication system introduces a `User` aggregate (distinct from `Creator`). Each `User` holds a per-user set of roles (`reader`, `uploader`, `moderator`, `admin`) stored as `text[]` with a CHECK constraint (`cardinality(roles) > 0` and each element in the four-role set); reads are anonymous, writes are gated by an OR role-gate applied per-route via a `from_fn_with_state` middleware that injects `AuthenticatedUser { id, sid, roles }` into request extensions. Two Ed25519-signed JWT classes are issued at `POST /sessions` (login): a stateless 15-min access JWT (`typ: "at+jwt"`, claims `sub`/`sid`/`role`/`iat`/`exp`) returned in the JSON body for in-memory JS storage, and a 30-day refresh JWT (`typ: "rt+jwt"`, claims `sub`/`sid`/`jti`/`iat`/`exp`) issued in an `HttpOnly; Secure; SameSite=Strict; Path=/sessions; Max-Age=2592000` cookie. Signing keypairs are per-class, loaded from `APP_JWT_ACCESS__KEY`/`APP_JWT_REFRESH__KEY` as file paths to raw 32-byte Ed25519 seeds, with the public key derived in-memory at startup. `typ` (RFC 9068 `at+jwt` plus the project's analogous `rt+jwt`) at the JOSE-header level prevents token-class confusion; the alg is pinned server-side to `EdDSA` and `none` is rejected.

Refresh tokens are tracked in two Redis structures per user: a sibling SET `sids:<sub>` listing the user's active session ids (sid), and per-session STRING keys `refresh-tokens:<sub>:<sid>` carrying the session JSON `{"jti": "<KeyedBLAKE3(jti)>", "ua", "ip", "created_at", "updated_at"}` with a native Redis TTL of the refresh-token lifetime (30 d). `created_at` is set at login and never mutated; `updated_at` is bumped on each `/sessions/refresh`. `POST /sessions/refresh` extracts `sub`/`sid`/`jti` from the verified JWT, `GET refresh-tokens:<sub>:<sid>` to load the session JSON, compares `keyed_blake3(jti)` to the stored value, and on match issues a new refresh JWT with a fresh `jti` and bumps `updated_at`, then pipelines `SET refresh-tokens:<sub>:<sid> <new_json> EX 2592000` (per-session TTL reset to 30 d), `SADD sids:<sub> <sid>` (idempotent), and `EXPIRE sids:<sub> 2592000` (SET TTL rolled forward to 30 d) in one atomic `MULTI`/`EXEC` round-trip; on mismatch it `tracing::warn!`s and returns 401 -- there is no reuse-detection / family-revocation escalation, only a log signal. `DELETE /sessions/all` deletes every entry keyed by `SMEMBERS sids:<sub>` (each `refresh-tokens:<sub>:<sid>`) plus `DEL sids:<sub>`. `DELETE /sessions/me/current` logs the requester out by substituting the JWT's sid server-side (no path sid passed); it bypasses the 24h rule so a freshly-logged-in user can always log themselves out. `DELETE /sessions/me/{sid}` revokes a specific one of the requester's own other sessions; the path sid is ownership-checked via `SISMEMBER sids:<sub> <sid>`. The 24h-revoke-protection rule applies to `DELETE /sessions/all` and `DELETE /sessions/me/{sid}`: if the requester's session `created_at` is within the last 24h, the request is rejected with 409 Conflict -- an attacker who just compromised credentials cannot immediately lock out the user's other sessions. `GET /sessions/me` reads `SMEMBERS sids:<sub>` then `MGET refresh-tokens:<sub>:<sid> ...`, returning the JSON pairs whose per-session keys are still alive and lazily `SREM`-ing the others (native TTL may clear a per-session key before `sids:<sub>` is updated, so the SET is a superset-of-alive filtered on read). `POST /sessions` (login) uses the same pipelined write pattern as refresh: `SET refresh-tokens:<sub>:<sid> <json> EX 2592000` + `SADD sids:<sub> <sid>` + `EXPIRE sids:<sub> 2592000`. The Redis client is `redis` with `ConnectionManager` (auto-reconnecting multiplexed connection); BLAKE3 is keyed with an env pepper (`APP_BLAKE3__KEY`) distinct from the JWT signing keys.

Passwords are hashed with Argon2id (`argon2` crate) using params loaded from `APP_PASSWORD__M_COST`/`APP_PASSWORD__T_COST`/`APP_PASSWORD__P_COST` via `envious` + `serde`, stored as the PHC string in a single `password_hash TEXT` column (per-user salt embedded in the PHC, no pepper). Password policy is length 16-128 with no composition rules (NIST SP 800-63B). Registration (`POST /users`) is open for the default `{reader}` role. Moderator and Admin share the content-moderation gate (`require_roles([Moderator, Admin])`); Admin alone gates user-promotion (`require_roles([Admin])`) -- the privilege gap is enforced by routing, not by role hierarchy. Moderator may grant or revoke the `Uploader` role for other Users; Admin may grant or revoke any role. Grant and revocation are `array_append`/`array_remove` on `users.roles` (promotion endpoint deferred from v1). Login identifier is email (`POST /sessions` takes an `email` field despite `username` also being unique); `Email` and `Username` are newtypes with `TryFrom<String>` validation in the entity layer -- `Email` via `validator::validate_email`, `Username` via the regex `^[a-zA-Z0-9_]{3,32}$` (no `validator` derive macros, mirroring the `Name` pattern). Email verification is deferred for v1 but `verified_at timestamptz null` is reserved on `users`.

Routes follow plural REST (ADR-0002) with `{data}` envelope. `/users`: `POST /users` (register, anonymous), `GET /users/me` (current user). `/sessions`: `POST /sessions` (login, anonymous-via-credentials), `POST /sessions/refresh` (refresh-cookie; the one action sub-resource -- a pragmatic breach of pure REST), `DELETE /sessions/all` (logout-all, payload from JWT; gated by the 24h rule), `DELETE /sessions/me/current` (self-logout; server uses JWT sid, no path sid needed; exempt from the 24h rule), `DELETE /sessions/me/{sid}` (revoke one of the requester's own other sessions; gated by the 24h rule), `GET /sessions/me` (list own sessions as `sid`/`ua`/`ip`/`created_at`/`updated_at` with `jti` scrubbed server-side). `me`, `current`, `all`, `refresh` are reserved path aliases (`me`/`current`/`all` cannot collide with UUID ids/sids; `refresh` cannot collide either) and must register before the `{sid}` pattern in the router. Error map: 400 parse / 401 unauthenticated / 403 role-gate fail / 404 `sub` deleted on `/users/me` / 409 duplicate email-or-username on `POST /users`, OR 24h-revoke-protection block on `DELETE /sessions/all` and `DELETE /sessions/me/{sid}` / 422 semantic / 500 internal; 401 reveals only "Invalid credentials", 403 reveals only "Forbidden". The 409 choice for duplicate email-or-username supersedes ADR-0002's 422 for duplicate-creator-name (RFC 9110 §15.5.10 places a "conflict with current state of the target resource" -- which a duplicate-content state conflict satisfies -- in 409, while 422 is reserved for content-shape semantic violations such as regex miss or out-of-range length; ADR-0002's prose is unchanged but its Status frontmatter records the partial supersession). New deps: `argon2`, `jsonwebtoken`, `blake3`, `redis` (with `tokio-comp`), `validator`, `regex`. `secrecy` was already in `Cargo.toml` for env secret wrapping.

Rejecting the `/auth/*` action namespace (RFC 6749-style) in favour of plural resources under `/users` and `/sessions` keeps the surface consistent with ADR-0002. Rejecting stateful access tokens (whitelist/denylist per-token) preserves the handoff's "CPU-only, zero DB queries on protected requests" property -- at the cost of an up-to-15-min window where a logged-out user's access JWT keeps working (mitigated by short TTL). Rejecting the per-user HASH model in favour of per-session STRING keys with native Redis TTL makes per-session expiry authoritative (TTL lives with the data it governs) instead of split between HASH-level Redis TTL and handler-side `expires_at` checks; the `sids:<sub>` SET is kept alongside as a lookup index so `GET /sessions/me` and `DELETE /sessions/all` can use `SMEMBERS`+`MGET` rather than SCAN over the keyspace (SCAN MATCH `refresh-tokens:<sub>:*` walks the entire keyspace, which is O(keyspace) per request and becomes unusable around ~100k keys). Rejecting reuse-detection state (`previous_jti` or a used-jti SET) simplifies the session JSON at the cost of a breach alarm -- the warn-log signal replaces it. Rejecting `citext` for email keeps canonicalisation at the entity layer.
