# Manga catalog schema: CHECK-enum collapse, layered chapters/releases/pages, and asymmetric localization

The pre-existing `book_types`, `book_statuses`, and `label_types` lookup tables are collapsed into `CHECK` constraints on their owning columns (`books.type`, `books.status`, `labels.type`), per `docs/sql.md`'s existing "no PG enum type, use check constraints" convention -- these are genuinely closed, small, stable sets (three publication formats, four statuses, two label kinds). `content_ratings` and `languages` stay standalone tables and keep their `GET` list endpoints: content rating systems vary by country and the project explicitly wants room to support more than DC Comics' scale later, and the language set is the full ISO 639 list, neither of which is a closed enum.

Chapters are modeled across three tables instead of one, to support scanlation-style parallel releases: `chapters` is an abstract numbered slot (`book_id`, `number`, `name`, `volume`) carrying no language and no page images; `chapter_releases` is a single-language, single-upload content row; `chapter_pages` are the images belonging to one release. This layering exists specifically so the same `Chapter Number` can have multiple independent page-sets -- different languages, or competing releases in the same language from different uploads -- as clean FK-linked rows, rather than `chapter_pages` needing a composite disambiguation key bolted onto a flat `chapters`-owned table. The release container itself is fixed after creation -- its `chapter_id` and `language_id` never change, there is no `PUT` on `chapter_releases`, and it carries only `created_at` -- but its pages are independently mutable: a page's image can be replaced in place, and pages can be inserted, removed, or reordered, each operation shifting `sort_order` to keep the set contiguous from 1. `chapter_pages` carries `updated_at` for this reason. `book_covers` follows the identical pattern for the same reason -- an uploader can pick the wrong image for either -- gaining the same in-place-replace / insert / reorder / delete surface and its own `updated_at` column.

`chapters.number` is `real` (Postgres) / `f32` (Rust), not `smallint` or `numeric`. Chapter numbers need fractional values for specials/omakes ("Chapter 12.5"), ruling out `smallint`; `real` was chosen over `numeric` to avoid adding a decimal-type dependency (`rust_decimal`/`bigdecimal`) that `sqlx` would otherwise require. This is safe specifically because chapter numbers are write-once literals that are only ever stored, compared, and sorted -- never computed -- so the float-precision risk that would normally rule out floats (accumulated rounding error across arithmetic) doesn't apply.

`uploaded_by` is deliberately absent from `books` and `chapter_releases` for v1. No `users` table exists yet -- ADR-0003 designed the auth system on paper but it was never implemented -- and the catalog is shipping before auth so neither depends on the other's timeline. `uploaded_by` will be added via an additive migration once auth ships, in whatever shape it ends up taking.

`book_titles` caps at 12 rows per book, enforced at both the request-validation layer (rejecting an oversized `titles` array with 422 before any write reaches the database) and a database trigger (`enforce_book_titles_limit`) as a backstop. This is the only trigger anywhere in the schema, and the duplication is deliberate rather than an oversight -- the trigger is cheap insurance against a future write path to `book_titles` that bypasses request validation; in normal operation it should never fire, since the app check runs first.

`book_titles` and `chapter_localizations` intentionally use different shapes for similar-looking data. `book_titles` has a surrogate `id` primary key and allows more than one row per `(book_id, language_id)`, up to the 12-per-book cap -- a book can accumulate several alternate English names or an original non-English title -- with no English row mirrored in, since `books.name` is already the always-present canonical English name and `book_titles` holds only additions to it. `chapter_localizations` keeps its original composite `(chapter_id, language_id)` primary key, exactly one row per language, with English mirrored in: chapter titles don't have the "many alternate names" use case book titles do, and the mirror is what lets a reader-facing "English | original language" chapter title be built from one uniform query instead of branching on whether the chapter's original language is English. `chapter_localizations` folds into `POST`/`PUT /books/{id}/chapters/{chapter_id}` the same way `book_titles` folds into the book body (see ADR-0005) -- blind full-array replace, no separate `/chapters/{id}/localizations` endpoint, no per-row timestamps. This doesn't reintroduce the coupling that keeps titles off `chapter_releases` in the first place: resending a chapter's full set of short text rows on every edit is free in a way resending a release's page images would not be.
