# A book's covers are an unordered gallery with one flagged main image, never replaced in place

`/books/{id}/covers` supports exactly `POST` (a new image), `GET` (the gallery), and `DELETE` (one image), plus `PUT /books/{id}/main-cover` to promote one. No `PUT` on a cover, no `PATCH` anywhere. Fixing a wrong upload is `POST` the replacement then `DELETE` the original, in that order so a failed upload can never leave a book with fewer covers than it started with (ADR-0005's ordering argument, one level up). *Rejected: a dedicated replace endpoint -- a second upload path duplicating sniffing, size limit, and storage-then-database ordering just to preserve an id. A "replaced" cover getting a new id is only a loss if a cover had identity worth preserving, and it has none: a cover is an image and nothing else.*

**No order.** An earlier design gave each cover a `sort_order` and derived the main `Cover` as the lowest -- but ordering makes every other decision expensive: a value that only means something relative to its siblings turns each single-row write into a statement about all of them, forcing `max(sort_order) + 1` on insert, a unique constraint, a deferrable declaration, a row lock against two uploads claiming one position, and a retry path for the remaining races. Only the main image needed to be selectable, so ordering was dropped for a single `is_main` flag -- and every one of those mechanisms went with it.

**The flag lives on `book_covers`, not as a `main_cover` pointer on `books`.** A pointer gives uniqueness for free, but `book_covers.book_id` already references `books`, so a pointer back creates a FK cycle with the insert/delete ordering constraints that implies. Uniqueness is instead a partial unique index, `on book_covers(book_id) where is_main`. It can't be a table constraint -- PostgreSQL `UNIQUE` constraints can't be partial; the exclusion-constraint form needs `btree_gist`; encoding "not main" as `NULL` buys a plain unique constraint at the price of three-valued logic and a `NULLS LAST` on every read. A partial unique index enforces the invariant just as strongly -- Postgres implements unique constraints as unique indexes anyway.

**Promotion** must demote before promoting, because a partial unique index can't be deferred: `set is_main = false where book_id = $1 and is_main`, then `set is_main = true where id = $2 and book_id = $1`. In that order the index is empty between statements and nothing collides; the reverse order, or a single `is_main = (id = $2)` statement, can trip the index mid-scan depending on row order. Those two statements in one transaction are the only transaction the feature adds -- upload, delete, and read are single statements, and deleting a book relies on `on delete cascade` exactly as `book_links`/`book_titles`/`book_labels` already do. Two clients promoting different covers at once produce `23505` on the loser, returned as 409 per RFC 9110 §15.5.10 -- the reading ADR-0002 applies to duplicate creator names.

**No timestamps.** The image is immutable once uploaded (no replace), the uuid v7 id already encodes creation time, and the only mutable field is a flag whose current value is the whole truth -- so `created_at`/`updated_at` would be columns nobody reads. Matches `creators` (has `created_at`, no `updated_at`) and the book child tables (neither).

**Storage key** is the cover's bare uuid, in a dedicated bucket, computed rather than stored. *Rejected: storing it -- the column would hold `id.to_string()` on every row, a verbatim copy of the PK, correct only by construction.* What's stored instead is `extension` (`jpg`/`png`/`webp`), which the key doesn't need but `GET /books/{id}/covers` does, returning it per entry so a client knows the format without fetching bytes. Upload also sets `Content-Disposition: inline; filename="..."` on the object, the name taken from the upload's own filename (sanitised via `sanitize_filename`; a part carrying none is `422`) rather than derived from `{id}.{extension}`, so a browser save/open gets back the name it was given. Writing the disposition once at upload beats a `response-content-disposition` override recomputed and re-signed on every presign -- the presign then needs nothing from the row but the id, and the header is a property of the object, not the URL. Accepted trade: changing the key scheme later means renaming every object in the bucket (S3 has no atomic rename).

**Uploads** are `multipart/form-data` with exactly one image part, its field name ignored. A raw request body was the original design -- one image, no accompanying fields -- superseded once the upload's `Content-Disposition` needed a client-supplied filename a raw body has nowhere to carry. Format is sniffed from magic bytes, never the request's `Content-Type` (client-supplied and browser-derived from the file extension, so an honest rename makes it wrong); the stored `Content-Type` is set from the sniffed value, so nothing attacker-controlled is ever served back. A body over 5 MiB is refused before buffering, matching ADR-0006's per-page bound; an unrecognised format is 415, which RFC 9110 §15.5.16 extends to formats determined "as a result of inspecting the data directly". Image dimensions are deliberately not validated -- that means decoding untrusted image data in the request path, the largest attack surface here and a decompression-bomb vector, for a quality check the byte limit already bounds.

**`GET /books/{id}/covers`** returns the whole gallery, ordered by id, no pagination, no `nextCursor` -- a deliberate exception to ADR-0002's list convention, since a gallery has no cursorable order and no realistic unbounded growth. Each entry carries a relative `url` to the permanent per-cover route rather than a presigned URL, so a cached response never hands out expired links and the app never needs to know its own public origin (`Host`/`X-Forwarded-*` are client-controllable).

**Image bytes are not cached anywhere today** -- a deferred cost, not an oversight. The redirect carries no explicit freshness, and 302 isn't among RFC 9110 §15.1's heuristically cacheable codes, so every view reaches the application; worse, each presign produces a different URL, so a browser can't reuse bytes it already downloaded, and a catalog grid re-fetches every cover on every navigation. App cost is negligible (one indexed lookup, one HMAC per view), but the repeated downloads are real bandwidth against RustFS. The fix needs no architectural change: raise the presign TTL to hours/days and set `Cache-Control: public, max-age=N` (N comfortably below the TTL), letting the browser reuse both the redirect and target URL, and letting a future CDN work. Deferred because it trades a longer-lived signed URL for caching, and the signature protects nothing on a cover every Guest can already fetch unauthenticated -- better decided alongside whatever caching layer actually motivates it. (ADR-0009: per-cover image reads now `404` unless the owning `Book` is `Listed` or the caller can moderate.)
