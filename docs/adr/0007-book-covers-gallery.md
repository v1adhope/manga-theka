# A book's covers are an unordered gallery with one flagged main image, never replaced in place

`/books/{id}/covers` supports exactly three operations -- `POST` a new image, `GET` the gallery, `DELETE` one image -- plus `PUT /books/{id}/main-cover` to promote one of them. There is no `PUT` on a cover and no `PATCH` anywhere in the feature. Fixing a wrong upload is two calls, `POST` the replacement and then `DELETE` the original, in that order so that a failed upload can never leave a book with fewer covers than it started with (the same ordering argument as ADR-0005, one level up). A dedicated replace endpoint was rejected because it would be a second upload path, duplicating the sniffing, size limit, and storage-then-database ordering that `POST` already has to implement, in exchange for preserving an id. The cost is that a "replaced" cover is a different resource with a different id, which is only a loss if a cover has identity worth preserving -- and here it has none, since a cover is an image and nothing else.

The gallery has no order. An earlier design gave each cover a `sort_order` and derived the `Cover` as the lowest one, but ordering is the property that makes every other decision expensive: a value that only means something relative to its siblings turns each single-row write into a statement about all of them, which forced `max(sort_order) + 1` on insert, a unique constraint, a deferrable declaration so a permutation could be written without tripping it mid-statement, a row lock to stop two uploads claiming the same position, and a retry path for the races that remained. Only the main image actually needed to be selectable, so the ordering was dropped and replaced with a single `is_main` flag. Every one of those mechanisms went with it.

The flag lives on `book_covers`, not as a `main_cover` pointer on `books`. A pointer would have given uniqueness for free -- a column holds one value -- but `book_covers.book_id` already references `books`, so a pointer back would create a foreign key cycle between the two tables, with the ordering constraints on insert and delete that a cycle implies. Uniqueness is instead enforced by a partial unique index, `on book_covers(book_id) where is_main`. It cannot be expressed as a table constraint, because `UNIQUE` constraints in PostgreSQL cannot be partial; the exclusion-constraint form needs the `btree_gist` extension, and encoding "not main" as `NULL` to reuse a plain unique constraint buys a keyword at the price of three-valued logic and a `NULLS LAST` clause on every read. A partial unique index enforces the invariant exactly as strongly -- PostgreSQL implements unique constraints as unique indexes anyway.

That index also dictates how promotion is written. A partial unique index cannot be deferred, so the two updates must demote before they promote: `set is_main = false where book_id = $1 and is_main`, then `set is_main = true where id = $2 and book_id = $1`. In that order the index is empty between the statements and nothing can collide; the reverse order, or a single statement setting `is_main = (id = $2)`, can trip the index mid-scan depending on row order. Those two statements in one transaction are the only transaction the feature adds. Everything else -- upload, delete a cover, read the gallery -- is a single statement, and deleting a book relies on `on delete cascade` exactly as `book_links`, `book_titles`, and `book_labels` already do. Two clients promoting different covers at the same instant produce a `23505` on the loser, returned as 409 per RFC 9110 section 15.5.10, which is the same reading ADR-0002 applies to duplicate creator names.

Covers carry no timestamps. The image is immutable once uploaded (there is no replace), the uuid v7 id already encodes creation time, and the only mutable field is a flag whose current value is the whole truth -- so `created_at` and `updated_at` would both be columns nobody reads. This matches `creators`, which carries `created_at` and no `updated_at`, and the book child tables, which carry neither.

The storage key is the cover's bare uuid, in a bucket dedicated to covers, and it is computed rather than stored. Storing it was considered at length, on the argument that Postgres and RustFS share no transaction so the database ought to record what was actually written; it was rejected because with this key scheme the column would hold `id.to_string()` on every row -- a verbatim copy of the primary key that can only ever be correct by construction or wrong by bug. What is stored instead is the image's `extension`, constrained to `jpg`, `png`, or `webp`, which the key does not need but the read path does: `GET /books/{id}/covers/{coverId}/image` uses it to set `response-content-disposition` on the presigned URL, so an image opened or saved from a browser arrives with a usable filename instead of an extensionless blob. The accepted trade is that changing the key scheme later means renaming every object in the bucket, since S3 has no atomic rename.

Uploads are the raw request body, not `multipart/form-data`. Multipart exists to carry several named fields in one request, and a cover upload has exactly one image and no accompanying fields, so the boundary framing and part headers would be pure overhead around a payload that can simply be the body. The format is decided by sniffing magic bytes, never from the request's `Content-Type`: that header is client-supplied, and a browser derives it from the file extension, so an honest user renaming a file is enough to make it wrong. The object's stored `Content-Type` is set from the sniffed value, so nothing attacker-controlled is ever served back from the storage domain. A body over 5 MiB is refused before buffering, matching the per-page bound ADR-0006 assumes for chapter pages; an unrecognised format is 415, which RFC 9110 section 15.5.16 explicitly extends to formats determined "as a result of inspecting the data directly". Image dimensions are deliberately not validated -- doing so means decoding untrusted image data in the request path, which is both the largest attack surface available here and a decompression-bomb vector, in exchange for a quality check the byte limit already bounds the damage of.

`GET /books/{id}/covers` returns the whole gallery, ordered by id, with no pagination and no `nextCursor` -- a deliberate exception to ADR-0002's list convention, since a gallery has no cursorable order and no cap that would make it grow without bound in practice. Each entry carries a relative `url` pointing at the permanent per-cover image route rather than a presigned URL, so a cached gallery response never hands a client links that have since expired, and the application never has to know its own public origin (`Host` and `X-Forwarded-*` are client-controllable, and the alternative is a configured base URL plus a class of wrong-host bugs behind a proxy).

Image bytes are not cached anywhere today, and that is a deferred cost rather than an oversight. The redirect carries no explicit freshness, and 302 is not among the heuristically cacheable status codes in RFC 9110 section 15.1, so every view reaches the application; more importantly, each presign produces a different URL, so a browser's own cache cannot reuse the bytes it already downloaded and a catalog grid re-fetches every cover on every navigation. The application cost is negligible -- one indexed lookup and one HMAC per view, with no image bytes transiting the process -- but the repeated downloads are real bandwidth against RustFS. The fix needs no architectural change: raise the presign TTL to hours or days and set a `Cache-Control: public, max-age=N` on the redirect with `N` comfortably below the TTL, which makes the browser reuse both the redirect and the target URL, and makes a CDN work if one ever appears. It is deferred because it trades a longer-lived signed URL for caching, and the signature protects nothing on a cover that every Guest can already fetch without authenticating -- so the decision is better made alongside whatever caching layer actually motivates it.
