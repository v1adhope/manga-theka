# Book labels, links, titles, and creators are embedded in the book payload, not separate endpoints

A book's `Label`s, `Book Link`s, and `Alternative Title`s are arrays inside `POST`/`PUT /books`, read back embedded in `GET /books/{id}`. No `/books/{id}/labels`, `/links`, or `/titles` endpoints. `label_ids` resolves to existing `labels` rows by id (attach-by-reference, per the project's "requests carry only ids for nested entities" rule); `titles` and `links` are value data (`{language_id, name}` / `{kind, url}`). All three are full-array-replace on every write, not diffed -- none of `book_labels`, `book_titles`, `book_links` carry a timestamp a partial diff would preserve, so blind replace loses nothing.

**Creators** are embedded the same way, attach-by-reference via a `creators` array of `{creatorId, role}`, replaced wholesale. Role isn't a property of `Creator` -- a `Creator` row is identity (name) only, since the same person is routinely both Artist and Author, sometimes on one book. Role lives on `book_creators`, one row per `(book, creator, role)` with `role` in the PK so a creator can be credited twice on one book. `GET /books` and `GET /books/{id}` aggregate credits into a `roles` array (`array_agg` grouped by creator, at the SQL layer). *Rejected: `role` on `creators`, giving a dual-role person two identity rows -- `GET /creators/{id}` for their Author row wouldn't show Artist-credited books, and any future creator-profile or merge feature would have to reconcile the split.*

**Covers stay a separate endpoint** (`/books/{id}/covers`); creation-time merging was rejected. Cover uploads are raw-body writes to RustFS with no transaction spanning RustFS and Postgres, so write order is fixed to keep the only failure harmless: object uploaded and confirmed in RustFS first, `book_covers` row inserted only after. A failed upload never reaches Postgres; a Postgres insert failing after a successful upload orphans an unreferenced, client-invisible object, left as-is (reconciliation sweep deferred). The reverse order (DB row first) is rejected outright: it can leave a `book_covers` row addressing an object never written, breaking reads instead of failing safely. That ordering would make merging safe too, but `/books/{id}/covers` stays separate regardless -- it must exist anyway for the gallery lifecycle (more covers, promoting a main image, deletion), so merging would only duplicate cover-creation logic; and a failed standalone upload leaves the book in an already-valid state (no cover, retry alone) where a failed merged request would tempt a book-duplicating retry. Labels, links, and titles have no such failure mode -- plain rows referencing already-validated data -- so folding them in doesn't reintroduce the risk (covers model: ADR-0007).

**Shallow nesting.** A collection lives under its parent (creating/listing need the parent to scope them); an individual member is addressed by its own id alone -- so `POST`/`GET /books/{id}/chapters` but `GET`/`PUT`/`DELETE /chapters/{id}`, and `GET /releases/{release_id}/pages/{page_number}` flat (ADR-0006), two levels below books. Member queries still carry `book_id = $2` alongside the PK -- not to find the row, but so `GET /books/{wrongBook}/chapters/{c}` 404s instead of returning a chapter whose `bookId` contradicts its path. That predicate stays load-bearing while the URL asserts parentage and costs nothing.

**A chapter's book is immutable**: `book_id` is set once from the path on `POST /books/{id}/chapters`, `update_chapter.sql` omits it from `SET`, `PUT` has no `bookId` field. The route builds `Chapter` with a `Uuid::nil()` placeholder for that field, as ADR-0002's `update_creator` uses `UNIX_EPOCH` for immutable `created_at` -- both preserve a non-`Option` entity invariant for a column the update never writes. Correcting a mis-filed chapter is delete-and-recreate. `GET` returns `bookId`, the only place the parent link is expressed.
