# Book labels, links, and titles are embedded in the book payload, not separate endpoints

Unlike covers (own CRUD endpoint group under `/books/{id}/covers`) and chapters (created and listed under `/books/{id}/chapters`, then addressed individually at `/chapters/{id}`), a book's `Label`s, `Book Link`s, and `Alternative Title`s are written as arrays inside `POST`/`PUT /books` and read back embedded in `GET /books/{id}`. No `/books/{id}/labels`, `/books/{id}/links`, or `/books/{id}/titles` endpoints exist. `label_ids` resolves to existing `labels` rows by id (attach-by-reference, matches the project's "API requests include only ids for nested entities" rule); `titles` and `links` are value data (`{language_id, name}` / `{kind, url}`) replaced wholesale. All three are full-array-replace on every book write, not diffed -- none of the three underlying tables (`book_labels`, `book_titles`, `book_links`) carry a `created_at`/`updated_at` that a partial diff would need to preserve, so blind replace loses nothing.

A book's `Creator`s are embedded on the read side only for now: `GET /books` and `GET /books/{id}` return the resolved `creators` array, while `POST`/`PUT /books` take no `creator_ids` yet. Attaching them by id on write follows later, in the same shape as `label_ids`.

Covers stay a separate endpoint on purpose, and creation-time merging was considered and rejected. Cover uploads are raw-body writes to RustFS, and there's no cross-system transaction spanning RustFS and Postgres, so the write order is fixed to keep the only possible failure harmless: the object is uploaded and confirmed in RustFS first, and only then is `book_covers` inserted. If the upload fails, nothing reaches Postgres. If the Postgres insert fails after a successful upload, the object is orphaned -- unreferenced, invisible to clients, and left as-is; a reconciliation sweep to reclaim orphaned objects is deferred to a future issue rather than built now. The reverse order (DB row first) is rejected outright, since it can leave a `book_covers` row addressing an object that was never written, breaking reads instead of failing safely.

That ordering would make it technically safe to create a book and its first cover in one request too, but `/books/{id}/covers` stays separate regardless. It has to exist anyway for the gallery's full lifecycle -- more covers, promoting one as the main image, deletion, all on an already-existing book -- so merging would only duplicate cover-creation logic rather than replace it. A failed standalone upload also leaves the book in an already-valid state (no cover yet, retried alone), where a failed merged request would tempt the client to retry the whole call and create a duplicate book. Labels, links, and titles have no such failure mode: they're plain rows referencing or containing already-validated data, so folding them into the book payload doesn't reintroduce the risk covers were split out to avoid. The covers gallery's own model -- its endpoint set, why it carries no ordering, and how the main image is chosen -- is recorded in `docs/adr/0007-book-covers-gallery.md`.

Child resources follow a shallow-nesting rule: a collection lives under its parent, because creating and listing both need the parent to scope them, but an individual member is addressed by its own id alone. So `POST`/`GET /books/{id}/chapters` but `GET`/`PUT`/`DELETE /chapters/{id}`. Chapters were originally nested the whole way down, and the member queries carried a `book_id = $2` alongside the primary key -- not to find the row, which the id already does, but to make `GET /books/{wrongBook}/chapters/{c}` a 404 instead of returning a chapter whose own `bookId` contradicted the path it arrived on. That predicate is load-bearing for as long as the URL asserts parentage, and costs nothing (a filter applied to one already-fetched row), so it was not the reason to change. The reason was ADR-0006, which specs `GET /releases/{release_id}/pages/{page_number}` flat, two levels below books: shallow nesting was already the recorded direction and chapters were the outlier. Nesting honestly all the way down ends at `/books/{b}/chapters/{c}/releases/{r}/pages/{n}`.

A chapter's book is immutable. Nothing in the write path can change it: `book_id` is set once from the path on `POST /books/{id}/chapters`, `update_chapter.sql` omits it from the `SET` clause, and the `PUT` body has no `bookId` field to send. The route constructs the `Chapter` value with a `Uuid::nil()` placeholder for the ignored field, the same way ADR-0002 records `update_book` using a `UNIX_EPOCH` placeholder for the equally immutable `created_at` -- both preserve a non-`Option` entity invariant for a column the update never writes. Correcting a chapter filed under the wrong book is a delete and a re-create, not an edit. `GET` returns `bookId` in the payload, which is now the only place the parent link is expressed.
