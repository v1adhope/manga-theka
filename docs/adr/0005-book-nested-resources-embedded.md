# Book labels, links, and titles are embedded in the book payload, not separate endpoints

Unlike covers (own CRUD group under `/books/{id}/covers`) and chapters (created/listed under `/books/{id}/chapters`, addressed individually at `/chapters/{id}`), a book's `Label`s, `Book Link`s, and `Alternative Title`s are arrays inside `POST`/`PUT /books`, read back embedded in `GET /books/{id}`. No `/books/{id}/labels`, `/links`, or `/titles` endpoints exist. `label_ids` resolves to existing `labels` rows by id (attach-by-reference, matching the project's "requests include only ids for nested entities" rule); `titles` and `links` are value data (`{language_id, name}` / `{kind, url}`) replaced wholesale. All three are full-array-replace on every write, not diffed -- none of the underlying tables (`book_labels`, `book_titles`, `book_links`) carry a `created_at`/`updated_at` a partial diff would need to preserve, so blind replace loses nothing.

A book's `Creator`s are embedded the same way, but role isn't a property of `Creator` -- a `Creator` row is just identity (name), since the same person is routinely both Artist and Author, sometimes on the same book, and role is a fact about their credit on that book, not about who they are. Role lives on `book_creators`, one row per `(book, creator, role)`; its primary key includes `role` so a creator can be credited twice on one book. `GET /books` and `GET /books/{id}` aggregate credits into a `roles` array (`array_agg` grouped by creator, at the SQL layer) rather than one entry per role. `POST`/`PUT /books` take a `creators` array of `{creatorId, role}`, attach-by-reference like `label_ids`, replaced wholesale like the other embedded arrays.

Rejected: keeping `role` on `creators`, giving a dual-role person two identity rows. That duplicates identity for one real person -- `GET /creators/{id}` for their Author row wouldn't show Artist-credited books -- and any future creator-profile or merge-duplicates feature would have to reconcile the split.

Covers stay a separate endpoint on purpose; creation-time merging was considered and rejected. Cover uploads are raw-body writes to RustFS, and there's no cross-system transaction spanning RustFS and Postgres, so write order is fixed to keep the only possible failure harmless: object uploaded and confirmed in RustFS first, `book_covers` inserted only after. A failed upload never reaches Postgres; a Postgres insert failing after a successful upload orphans the object -- unreferenced, invisible to clients, left as-is (a reconciliation sweep is deferred to a future issue). The reverse order (DB row first) is rejected outright: it can leave a `book_covers` row addressing an object never written, breaking reads instead of failing safely.

That ordering would make merging book-and-first-cover creation technically safe too, but `/books/{id}/covers` stays separate regardless. It has to exist anyway for the gallery's full lifecycle (more covers, promoting a main image, deletion) on an already-existing book, so merging would only duplicate cover-creation logic. A failed standalone upload also leaves the book in an already-valid state (no cover yet, retry alone), where a failed merged request would tempt a retry that duplicates the book. Labels, links, and titles have no such failure mode -- plain rows referencing or containing already-validated data -- so folding them into the book payload doesn't reintroduce the risk covers were split out to avoid. The covers gallery's own model is recorded in ADR-0007.

Child resources follow a shallow-nesting rule: a collection lives under its parent (creating/listing both need the parent to scope them), but an individual member is addressed by its own id alone -- so `POST`/`GET /books/{id}/chapters` but `GET`/`PUT`/`DELETE /chapters/{id}`. Chapters were originally nested the whole way down, with member queries carrying `book_id = $2` alongside the primary key -- not to find the row, but to make `GET /books/{wrongBook}/chapters/{c}` 404 instead of returning a chapter whose `bookId` contradicted its path. That predicate stays load-bearing as long as the URL asserts parentage and costs nothing, so it wasn't the reason to change; the reason was ADR-0006 specing `GET /releases/{release_id}/pages/{page_number}` flat, two levels below books -- shallow nesting was already the direction and chapters were the outlier. Nested honestly all the way down, the path would be `/books/{b}/chapters/{c}/releases/{r}/pages/{n}`.

A chapter's book is immutable: `book_id` is set once from the path on `POST /books/{id}/chapters`, `update_chapter.sql` omits it from the `SET` clause, and `PUT` has no `bookId` field. The route builds `Chapter` with a `Uuid::nil()` placeholder for that field, the same way ADR-0002's `update_creator` uses a `UNIX_EPOCH` placeholder for immutable `created_at` -- both preserve a non-`Option` entity invariant for a column the update never writes. Correcting a chapter filed under the wrong book is delete-and-recreate, not an edit. `GET` returns `bookId`, now the only place the parent link is expressed.
