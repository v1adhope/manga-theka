# Book labels, links, and titles are embedded in the book payload, not separate endpoints

Unlike covers (own CRUD endpoint group under `/books/{id}/covers`) and chapters (own CRUD endpoint group under `/books/{id}/chapters`), a book's `Label`s, `Book Link`s, and `Alternative Title`s are written as arrays inside `POST`/`PUT /books` and read back embedded in `GET /books/{id}`. No `/books/{id}/labels`, `/books/{id}/links`, or `/books/{id}/titles` endpoints exist. `label_ids` resolves to existing `labels` rows by id (attach-by-reference, matches the project's "API requests include only ids for nested entities" rule); `titles` and `links` are value data (`{language_id, name}` / `{type, url}`) replaced wholesale. All three are full-array-replace on every book write, not diffed -- none of the three underlying tables (`book_labels`, `book_titles`, `book_links`) carry a `created_at`/`updated_at` that a partial diff would need to preserve, so blind replace loses nothing.

Covers stay a separate endpoint on purpose, and creation-time merging was considered and rejected. Cover uploads are multipart writes to RustFS, and there's no cross-system transaction spanning RustFS and Postgres, so the write order is fixed to keep the only possible failure harmless: the object is uploaded and confirmed in RustFS first, and only then is `book_covers` inserted. If the upload fails, nothing reaches Postgres. If the Postgres insert fails after a successful upload, the object is orphaned -- unreferenced, invisible to clients, and left as-is; a reconciliation sweep to reclaim orphaned objects is deferred to a future issue rather than built now. The reverse order (DB row first) is rejected outright, since it can leave a `storage_key` pointing at an object that was never written, breaking reads instead of failing safely.

That ordering would make it technically safe to create a book and its first cover in one request too, but `/books/{id}/covers` stays separate regardless. It has to exist anyway for the gallery's full lifecycle -- more covers, reordering, replacement, deletion, all on an already-existing book -- so merging would only duplicate cover-creation logic rather than replace it. A failed standalone upload also leaves the book in an already-valid state (no cover yet, retried alone), where a failed merged request would tempt the client to retry the whole call and create a duplicate book. Labels, links, and titles have no such failure mode: they're plain rows referencing or containing already-validated data, so folding them into the book payload doesn't reintroduce the risk covers were split out to avoid.
