# Book labels, links, titles, and creators are embedded in the book payload, not separate endpoints

Unlike covers (own CRUD group under `/books/{id}/covers`) and chapters (created/listed under `/books/{id}/chapters`, addressed at `/chapters/{id}`), a book's `Label`s, `Book Link`s, and `Alternative Title`s are arrays inside `POST`/`PUT /books`, read back embedded in `GET /books/{id}`. No `/books/{id}/labels`, `/links`, or `/titles` endpoints. `label_ids` resolves to existing `labels` rows by id (attach-by-reference, per the project's "requests include only ids for nested entities" rule); `titles` and `links` are value data (`{language_id, name}` / `{kind, url}`) replaced wholesale. All three are full-array-replace on every write, not diffed -- none of `book_labels`, `book_titles`, `book_links` carry a `created_at`/`updated_at` a partial diff would preserve, so blind replace loses nothing.

**Creators** are embedded the same way, but role isn't a property of `Creator` -- a `Creator` row is just identity (name), since the same person is routinely both Artist and Author, sometimes on one book. Role lives on `book_creators`, one row per `(book, creator, role)`; `role` is in the PK so a creator can be credited twice on one book. `GET /books` and `GET /books/{id}` aggregate credits into a `roles` array (`array_agg` grouped by creator, at the SQL layer) rather than one entry per role. `POST`/`PUT /books` take a `creators` array of `{creatorId, role}`, attach-by-reference like `label_ids`, replaced wholesale.

*Rejected: keeping `role` on `creators`, giving a dual-role person two identity rows -- `GET /creators/{id}` for their Author row wouldn't show Artist-credited books, and any future creator-profile or merge-duplicates feature would have to reconcile the split.*

**Covers stay a separate endpoint on purpose**; creation-time merging was rejected. Cover uploads are raw-body writes to RustFS with no cross-system transaction spanning RustFS and Postgres, so write order is fixed to keep the only possible failure harmless: object uploaded and confirmed in RustFS first, `book_covers` row inserted only after. A failed upload never reaches Postgres; a Postgres insert failing after a successful upload orphans an unreferenced, client-invisible object, left as-is (reconciliation sweep deferred). The reverse order (DB row first) is rejected outright: it can leave a `book_covers` row addressing an object never written, breaking reads instead of failing safely. That ordering would make merging book-and-first-cover creation safe too, but `/books/{id}/covers` stays separate regardless -- it has to exist anyway for the gallery lifecycle (more covers, promoting a main image, deletion) on an existing book, so merging would only duplicate cover-creation logic; and a failed standalone upload leaves the book in an already-valid state (no cover yet, retry alone) where a failed merged request would tempt a book-duplicating retry. Labels, links, and titles have no such failure mode -- plain rows referencing or containing already-validated data -- so folding them into the book payload doesn't reintroduce the risk covers were split out to avoid (covers gallery model: ADR-0007).

**Shallow nesting.** A collection lives under its parent (creating/listing both need the parent to scope them), but an individual member is addressed by its own id alone -- so `POST`/`GET /books/{id}/chapters` but `GET`/`PUT`/`DELETE /chapters/{id}`. Chapters were originally nested the whole way down, with member queries carrying `book_id = $2` alongside the PK -- not to find the row, but to make `GET /books/{wrongBook}/chapters/{c}` 404 instead of returning a chapter whose `bookId` contradicts its path. That predicate stays load-bearing as long as the URL asserts parentage and costs nothing, so it wasn't the reason to change; the reason was ADR-0006 specing `GET /releases/{release_id}/pages/{page_number}` flat, two levels below books -- shallow nesting was already the direction and chapters were the outlier. (Nested honestly all the way down: `/books/{b}/chapters/{c}/releases/{r}/pages/{n}`.)

**A chapter's book is immutable**: `book_id` is set once from the path on `POST /books/{id}/chapters`, `update_chapter.sql` omits it from the `SET` clause, and `PUT` has no `bookId` field. The route builds `Chapter` with a `Uuid::nil()` placeholder for that field, the same way ADR-0002's `update_creator` uses a `UNIX_EPOCH` placeholder for immutable `created_at` -- both preserve a non-`Option` entity invariant for a column the update never writes. Correcting a chapter filed under the wrong book is delete-and-recreate, not an edit. `GET` returns `bookId`, now the only place the parent link is expressed.
