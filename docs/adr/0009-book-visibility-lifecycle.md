# Book visibility is a five-state moderation lifecycle, separate from Book Status, shipped before auth as a state machine only

A `Book` gains a `visibility` axis -- `Draft`, `PendingReview`, `Listed`, `Rejected`, `Hidden` -- as a `CHECK`-constrained `text` column on `books` per `docs/sql.md`'s closed-set convention, entirely separate from `books.status`. `Book Status` (`Ongoing`/`Completed`/`Hiatus`/`Cancelled`) describes the work's progress; `CONTEXT.md` already scopes it to exclude "the catalog record's moderation or visibility state", and "published" was unavailable since ADR-0006 spends it on a `Chapter Release` published-by-having-a-committed-page. Merging the two would overload a four-value set meaning something orthogonal, so visibility gets its own column, `CONTEXT.md` term, and endpoint. `Book Status` is untouched.

Every `Book` is created `Draft`, and `POST /books` is open to any signed-in user (`Reader` and up), not just `Uploader` -- proposing a title is a personal action, publishing it is not. The only transition a submitter may make is `Draft -> PendingReview`; once submitted they can't pull it back, so a moderator always reviews a state the submitter can't mutate underneath them. Every other transition is a moderator action, all through one endpoint, `PUT /books/{id}/visibility` with `{ visibility, note? }`, guarded by a fixed table: `Draft -> {PendingReview, Rejected, Hidden}`, `PendingReview -> {Draft, Listed, Rejected, Hidden}`, `Listed -> {Hidden, Rejected}`, `Hidden -> {Listed, Rejected}`, `Rejected` terminal, plus every `X -> X`. `PendingReview -> Draft` is the sole way back into `Draft`: once a `Book` has been approved or hidden it never becomes a draft again, so `Draft` describes a title that has not yet been reviewed rather than a state anything can be demoted into. An illegal cell is `409` (the conflict-with-current-state reading ADR-0002 and ADR-0006 already apply); an unknown `visibility` in the body is `422`, while an unknown `?visibility=` in the query answers `400`, because that one is rejected by the framework's query deserializer before any handler runs -- the same answer `GET /feedback?kind=` already gives. This is the opposite of ADR-0006's per-verb RPC choice for release `commit`/`upload`, deliberately so: those are steps in an upload session, this is a single state transition whose target the client names, so a guard table beats six near-identical handlers.

A self-transition is legal and means "change only the note", which is why there is no `PUT /books/{id}/note`: one endpoint owns the column, and a note-only edit is just a move that happens to end where it started. Each `X -> X` obeys whatever note rule its own state already carries -- `Draft`, `Rejected`, and `Hidden` demand one, `Listed` takes an optional one and clears the note when it is omitted. `PendingReview -> PendingReview` rewrites the code-authored submit message and leaves `submitted_at` alone, so it is inert: a book under review cannot be annotated, and cannot lose its place in the queue.

`Rejected` is a moderator-set dead end -- a deferred sweeper reclaims rejected books and their media later, tracked as a future issue, not built now. Writes are tiered by state rather than merely frozen in two of them. `Draft` accepts the `Book` row and its covers, so a submitter assembles metadata and artwork before review, but not chapters, releases, or pages: content cannot precede approval, and a moderator therefore reviews a proposal rather than a library. `Listed` accepts everything. `PendingReview`, `Rejected`, and `Hidden` accept nothing, so review sees a stable snapshot, a rejected book stops changing before the sweeper reaches it, and a hidden book is inert the moment a complaint lands. Every refused write answers `409` naming the blocking state. `Hidden` being frozen is a reversal of this ADR's first draft, which let an uploader fix the reported problem in place: a book pulled from public view for cause should not keep changing while the cause is assessed, so the repair path is `Hidden -> Listed` and then an ordinary edit.

The whole feature ships before authentication exists: ADR-0003 designed auth on paper but it was never implemented, `books` has no `uploaded_by`, and issue 1 shipped the catalog deliberately auth-free. Enforcement of *who* may call a transition is a `// deferred: gate to <role>` comment at each handler naming the role that will guard it, nothing more; there are no `*_by` columns.

Reads split in two, and this is where the ADR diverges most from ADR-0006. *Metadata* is unlisted, not secret: `GET /books/{id}` and the by-id chapter and release routes serve a `Book` in any state to anyone holding the id, and only `GET /books` filters, to `Listed` by default with `?visibility=<value>` overriding it for the moderator queue. *Page content* is not. The rule is that a `Moderator` (or above) and the submitter may read pages in any state while everyone else reads only `Listed` ones -- an unapproved or withdrawn book must not be readable by the public merely because someone holds a release id, which is exactly the exposure ADR-0006 accepted for uncommitted releases and is not acceptable for a book pulled after a complaint. `GET /releases/{id}/pages`, `/pages/{page_number}`, `/pages/{page_id}/image`, and `GET /covers/{id}/image` all answer `404` unless the owning `Book` is `Listed` or the caller can moderate -- cover art is content too, and a `Book` hidden over its artwork must not keep serving it. The role half of the rule needs an identity, which ADR-0003's access JWT will supply. Until then a development stand-in reads `x-user-id` and `x-user-role` (comma-separated, or repeated) into an `Option<UserClaims>`, so the `Moderator`/`Admin` exemption is exercisable and testable today; a request asserting neither header is anonymous and extracts as `None`, while a half-stated or unreadable assertion is rejected with `401` rather than silently downgraded to a guest -- absent and malformed are different things, and neither yields privilege, so the failure mode is closed. **That header is client-asserted and is emphatically not a security boundary** -- it exists so the gate's shape is settled before ADR-0003's middleware replaces it, and it must be removed in the same change that lands real authentication. The submitter half stays deferred, since `books` still records no submitter to compare against; each gated handler carries a `// deferred` comment saying so. ADR-0006's "unlisted, not secret" claim now holds only for metadata, and its own text should be read with that carve-out.

The identity-free half of the design -- the legal-transition guard, the write tiers, the content gate -- is enforced now; the half needing a *trustworthy* identity -- who may call which transition, letting the submitter through the content gate, "only the submitter edits their own `Draft`" -- rides with issue 3. Blocking on auth was rejected: the state model and list filtering are independently useful.

This consciously diverges from ADR-0006's "no publish flag, no endpoint, no timestamp" stance, because books aren't releases. A release's published state is *derivable* -- at least one committed page, or not -- so a flag would duplicate a fact the pages already carry. "A human approved this book for the public catalog" is derivable from nothing, so it has to be stored. `books` gains `visibility text not null` (no column `default`; the initial `Draft` is written by the insert statement itself, per `docs/sql.md`), and `submitted_at timestamptz null`, since a review queue ordered by wait time needs it -- though the queue keeps the ordinary `id`-descending cursor and merely exposes `submittedAt` as a field, rather than growing a second pagination scheme for one query value. It does **not** gain `published_at` or `hidden_at`: reconstructable from an audit log once auth brings one, and adding them now is storage for a question nobody can ask yet. Nothing is deployed, so the columns join the original `books` migration instead of arriving as an alter-and-backfill. The list scan is supported by a composite `books(visibility, id)` index rather than a partial one on `where visibility = 'Listed'`: the filter is a bind parameter, so a partial index only helps when the planner can prove the parameter equals the predicate's literal, which a generic plan cannot. The composite index serves the default `Listed` scan and the moderator queue's `?visibility=` override alike, as an index-only scan whose ordering already matches the `id`-descending cursor.

Because every write and every page read must know the owning `Book`'s state, `chapter_releases` and `chapter_pages` each carry their own `book_id`, denormalized from their parent. Without it the lookup behind a release write is a two-table walk and the one behind a page read a three-table walk; with it every one is a single join. The column is never client-supplied -- each insert derives it from its parent row in the same statement -- so it cannot drift from the chapter's book. Its FK to `books` is `on delete restrict` too, so a surviving release or page now blocks `DELETE /books/{id}` directly, alongside the chapter-mediated route ADR-0006 describes. The guard itself is a `TryFrom` in the domain layer that consumes the requested transition and yields the validated command, so an unchecked move is unrepresentable rather than merely unwritten, and the write is a compare-and-swap on the current visibility rather than a locked read.

Moderator-to-submitter communication is a single nullable `note text` on `books`, capped at 2000 characters with a `check_length_books_note` backstop. It reuses the existing `Text` value object, which already rejects empty-or-whitespace and caps at 2000 for `Description` and `Feedback`; a `Note` newtype would have duplicated those rules exactly, so the domain keeps one type for the job. The note is submitter-visible, with deliberately no second staff-only field, since without auth nothing could keep one private and a speculative split isn't worth the column. It is written by code on `Draft -> PendingReview` (a fixed message telling the submitter their book is queued and roughly how long review takes), required and non-empty on any transition into `Draft`, `Rejected`, or `Hidden` (`422` if missing), and cleared on a move into `Listed` unless the caller supplies a replacement. A `book_review_notes` history table was rejected -- one overwritten field is enough until there's an audit log to hang history on. Two booleans (`is_draft`+`is_hidden`) instead of one enum were rejected for v1: the actor-and-reason distinction they'd preserve isn't recorded anywhere without an audit trail, and a single closed enum matches how `kind`/`status` are already modeled on this table -- revisit when auth lands.

The "someone requested the hide" channel is the separate `Feedback` entity, shipped in its own issue (submitted by a `Guest` or `User`, no `Role` required; `kind` one of `Report`/`Correction`/`General`; `status` one of `Open`/`Resolved`/`Dismissed`; optional `book_id` FK, `ON DELETE SET NULL` but non-null-required at `POST /feedback` for book-bound kinds). It has no foreign key back into the visibility machine -- a moderator reads a `Report` and calls `PUT /books/{id}/visibility` themselves, and the `hide` transition's `note` still carries the reason, since nothing links the two.
