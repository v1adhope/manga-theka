# Book visibility is a five-state moderation lifecycle, separate from Book Status, shipped before auth as a state machine only

A `Book` gains a `visibility` axis -- `Draft`, `PendingReview`, `Listed`, `Rejected`, `Hidden` -- stored as a `CHECK`-constrained `text` column on `books` per `docs/sql.md`'s closed-set convention, and entirely separate from `books.status`. `Book Status` (`Ongoing`/`Completed`/`Hiatus`/`Cancelled`) describes the progress of the work itself; `CONTEXT.md` already scoped it to explicitly exclude "the catalog record's moderation or visibility state", and "published" was unavailable as a name because ADR-0006 spends it on a `Chapter Release` that is published-by-having-a-committed-page. Merging the two would overload a four-value set that means something orthogonal, so visibility is its own column, its own `CONTEXT.md` term, and its own endpoint. `Book Status` is untouched.

Every `Book` is created `Draft`, and `POST /books` is open to any signed-in user (`Reader` and up), not just `Uploader` -- proposing a title is a personal action, publishing it is not. The only transition a submitter may make is `Draft -> PendingReview`; once submitted they cannot pull it back, so a moderator always reviews a state the submitter cannot mutate underneath them. Every other transition is a moderator action. Transitions run through one endpoint, `PUT /books/{id}/visibility` with `{ target, note? }`, guarded by a fixed table: `Draft -> {PendingReview, Rejected, Hidden}`, `PendingReview -> {Listed, Draft, Rejected}`, `Listed -> {Hidden, Rejected}`, `Hidden -> {Listed, Draft, Rejected}`, and `Rejected` terminal. An illegal cell is `409` (conflict with current state, the reading ADR-0002 and ADR-0006 already apply); an unknown enum value is `422`. This is the opposite of ADR-0006's per-verb RPC choice for release `commit`/`upload`, and deliberately so: those are steps in an upload session, this is a single state transition whose target the client names, so a guard table beats six near-identical handlers.

`Rejected` is set by a moderator and is a dead end -- a deferred sweeper reclaims rejected books and their media later, tracked as a future issue, not built now. `PendingReview` and `Rejected` both freeze the book: `PUT /books/{id}` and every create/update/delete on that book's chapters, covers, releases, and pages answer `409` while the book sits in either state, so review sees a stable snapshot and a rejected book stops changing before the sweeper reaches it. `Hidden` stays writable -- an uploader can fix the reported problem in place, then a moderator moves it back to `Listed` (or `Draft` for correction, or `Rejected`).

The whole feature ships before authentication exists. ADR-0003 designed the auth system on paper and it was never implemented, `books` still has no `uploaded_by`, and issue 1 shipped the catalog deliberately auth-free. So enforcement here is a `// deferred: gate to <role>` comment at each handler naming the role that will guard it, and nothing more; there are no `*_by` columns. The consequence is explicit and is the same one ADR-0006 accepted for uncommitted releases: a non-`Listed` book is *unlisted, not secret*. `GET /books/{id}` and the by-id chapter, release, and page routes still serve a `Draft`, `PendingReview`, `Rejected`, or `Hidden` book to anyone who has the id -- only the `GET /books` list is filtered, to `Listed` by default with `?visibility=<value>` overriding it for the moderator queue. The half of the design that needs no identity -- the legal-transition guard and the `PendingReview`/`Rejected` write freeze -- is enforced now; the half that needs one -- who may call which transition, restricting non-`Listed` reads to the submitter or a moderator, and a per-person "only the submitter edits their own `Draft`" rule -- rides with issue 3. Blocking this work on auth was rejected: the state model and list filtering are independently useful, and the secrecy gap closes exactly when ADR-0006's equivalent gap does.

This diverges from ADR-0006's "no publish flag, no publish endpoint, no publication timestamp" stance, consciously, because books are not releases. A release's published state is *derivable* -- it has at least one committed page or it does not -- so storing a flag would duplicate a fact the pages already carry. "A human approved this book for the public catalog" is derivable from nothing; there is no content fact that implies it, so it has to be stored. The `books` table gains `visibility text not null` (no column `default`; the `Draft` initial value is set in code per `docs/sql.md`), and `submitted_at timestamptz` null, because a review queue ordered by how long a book has been waiting needs it. It does **not** gain `published_at` or `hidden_at`: those are reconstructable from an audit log once auth brings one, and adding them now is storage for a question nobody can ask yet. Existing rows are backfilled to `Listed`, and a partial index `where visibility = 'Listed'` supports the default list scan.

Moderator-to-submitter communication is a single nullable `note text` on `books`, capped at 2000 characters (matching `Description`, via a `Note` newtype that rejects empty-or-whitespace when present) with a `check_length_books_note` backstop. It is submitter-visible; there is deliberately no second staff-only field, because without auth nothing could keep one private and a speculative split is not worth the column. The `note` is written by code on `Draft -> PendingReview` (a fixed "submitted, please be patient" message), is required and non-empty on any transition into `Rejected` or `Hidden` and on the return `-> Draft` (the reason, `422` if missing), and is cleared on `-> Listed` and `-> Hidden`-to-`Listed` unless the caller supplies a replacement. `PUT /books/{id}/note` sets or clears it without a transition, for a note on an already-`Listed` book. A `book_review_notes` history table was rejected: one overwritten field is enough until there is an audit log to hang history on. Two booleans (`is_draft` + `is_hidden`) instead of one enum were rejected for v1 -- the actor-and-reason distinction they preserve is not recorded anywhere without an audit trail, and a single closed enum matches how `kind` and `status` are already modeled on this table -- and can be revisited when auth lands.

The "someone requested the hide" channel from the grilling that produced this ADR is a separate `Feedback` entity in its own issue (submitted by a `Guest` or `User`, no `Role` required, with `kind` one of `Report`/`Correction`/`General`, `status` one of `Open`/`Resolved`/`Dismissed`, and an optional `book_id` foreign key that is `ON DELETE SET NULL` but non-null-required at `POST /feedback` for the book-bound kinds). It has no foreign key back into the visibility machine; a moderator reads a `Report` and then calls `PUT /books/{id}/visibility` themselves, and until it exists the `hide` transition's `note` carries the reason.
