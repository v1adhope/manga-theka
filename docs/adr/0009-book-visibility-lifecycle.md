# Book visibility is a five-state moderation lifecycle, separate from Book Status, shipped before auth as a state machine only

A `Book` gains a `visibility` axis -- `Draft`, `PendingReview`, `Listed`, `Rejected`, `Hidden` -- as a `CHECK`-constrained `text` column on `books` per `docs/sql.md`'s closed-set convention, entirely separate from `books.status`. `Book Status` (`Ongoing`/`Completed`/`Hiatus`/`Cancelled`) describes the work's progress; `CONTEXT.md` already scopes it to exclude moderation state, and "published" was unavailable since ADR-0006 spends it on a `Chapter Release`. Merging the two would overload a four-value set with an orthogonal meaning, so visibility gets its own column, `CONTEXT.md` term, and endpoint. This diverges from ADR-0006's "no publish flag, no endpoint, no timestamp" deliberately: a release's published state is *derivable* (has a committed page or not), so a flag would duplicate a fact the pages carry; "a human approved this book for the public catalog" is derivable from nothing, so it must be stored.

**Transitions.** Every `Book` is created `Draft`. `POST /books` is open to any signed-in user (`Reader` and up), not just `Uploader` -- proposing a title is personal, publishing it is not. The submitter's only move is `Draft -> PendingReview`, with no way to pull it back, so a moderator always reviews a state the submitter can't mutate underneath them. Every other transition is a moderator action through one endpoint, `PUT /books/{id}/visibility` with `{ visibility, note? }`, guarded by a fixed table:

- `Draft -> {PendingReview, Rejected, Hidden}`
- `PendingReview -> {Draft, Listed, Rejected, Hidden}`
- `Listed -> {Hidden, Rejected}`
- `Hidden -> {Listed, Rejected}`
- `Rejected` terminal
- every `X -> X`

`PendingReview -> Draft` is the sole way back into `Draft`: once approved or hidden a book never becomes a draft again, so `Draft` describes a title not yet reviewed rather than a state anything is demoted into. An illegal cell is `409` (the conflict-with-current-state reading of ADR-0002/0006); an unknown `visibility` in the body is `422`; an unknown `?visibility=` in the query is `400`, rejected by the framework's query deserializer before any handler runs (the same answer `GET /feedbacks?kind=` gives). This is the opposite of ADR-0006's per-verb RPC choice for `commit`/`upload`, deliberately so: those are steps in an upload session, this is a single state transition whose target the client names, so a guard table beats six near-identical handlers. The guard is a `TryFrom` in the domain layer consuming the requested transition and yielding the validated command, so an unchecked move is unrepresentable; the write is a compare-and-swap on the current visibility, not a locked read.

**Notes.** A self-transition is legal and means "change only the note" -- which is why there is no `PUT /books/{id}/note`: one endpoint owns the column. Each `X -> X` obeys its state's own note rule -- `Draft`, `Rejected`, `Hidden` demand a note; `Listed` takes an optional one and clears the note when it is omitted; `PendingReview -> PendingReview` rewrites the code-authored submit message, leaves `submitted_at` alone, and is inert (a book under review cannot be annotated and cannot lose its queue place).

The note is a single nullable `note text` on `books`, capped at 2000 characters with a `check_length_books_note` backstop, reusing the existing `Text` value object (already rejects empty-or-whitespace and caps at 2000 for `Description` and `Feedback`; a `Note` newtype would duplicate those rules). It is submitter-visible, with deliberately no second staff-only field, since without auth nothing could keep one private. It is written by code on `Draft -> PendingReview` (a fixed message: queued, review takes roughly X), required and non-empty on any transition into `Draft`, `Rejected`, or `Hidden` (`422` if missing), and cleared on a move into `Listed` unless the caller supplies a replacement. *Rejected: a `book_review_notes` history table (one overwritten field is enough until there's an audit log to hang history on); two booleans (`is_draft`+`is_hidden`) instead of one enum (the actor-and-reason distinction they'd preserve isn't recorded anywhere without an audit trail, and a single closed enum matches how `kind`/`status` are already modeled on this table).*

**Writes are tiered by state**, not merely frozen. `Draft` accepts the `Book` row and its covers, so a submitter assembles metadata and artwork before review, but not chapters, releases, or pages -- content cannot precede approval, so a moderator reviews a proposal rather than a library. `Listed` accepts everything. `PendingReview`, `Rejected`, and `Hidden` accept nothing, so review sees a stable snapshot, a rejected book stops changing before the sweeper reaches it, and a hidden book is inert the moment a complaint lands. Every refused write answers `409` naming the blocking state. `Hidden` being frozen reverses this ADR's first draft (which let an uploader fix the reported problem in place): a book pulled from public view for cause should not keep changing while the cause is assessed, so the repair path is `Hidden -> Listed` then an ordinary edit. `Rejected` is a dead end; a deferred sweeper reclaims rejected books and their media later.

**Reads split in two** -- the sharpest divergence from ADR-0006.

- *Metadata* is unlisted, not secret: `GET /books/{id}` and the by-id chapter and release routes serve a `Book` in any state to anyone holding the id; only `GET /books` filters, to `Listed` by default with `?visibility=<value>` overriding it for the moderator queue.
- *Page content* is not: a `Moderator` (or above) and the submitter may read pages in any state; everyone else reads only `Listed`. An unapproved or withdrawn book must not be publicly readable just because someone holds a release id -- the exposure ADR-0006 accepted for uncommitted releases, unacceptable for a book pulled after a complaint. `GET /releases/{id}/pages`, `/pages/{page_number}`, `/pages/{page_id}/image`, and `GET /covers/{id}/image` all answer `404` unless the owning `Book` is `Listed` or the caller can moderate -- cover art is content too. ADR-0006's "unlisted, not secret" now holds for metadata only.

**Auth is deferred; the state machine is not.** ADR-0003 designed auth on paper but it was never implemented, `books` has no `uploaded_by`, and issue 1 shipped the catalog deliberately auth-free. Enforcement of *who* may call a transition is a `// deferred: gate to <role>` comment at each handler, nothing more. The identity-free half -- the legal-transition guard, the write tiers, the content gate -- is enforced now; the half needing a *trustworthy* identity -- who may call which transition, letting the submitter through the content gate, "only the submitter edits their own `Draft`" -- rides with issue 3. Blocking on auth was rejected: the state model and list filtering are independently useful.

Until real auth, a development stand-in reads `x-user-id` and `x-user-role` (comma-separated, or repeated) into an `Option<UserClaims>`, so the `Moderator`/`Admin` exemption is exercisable and testable today. A request asserting neither header is anonymous (`None`); a half-stated or unreadable assertion is `401`, not a silent downgrade to guest -- absent and malformed are different, and neither yields privilege. **That header is client-asserted and emphatically not a security boundary**; it exists so the gate's shape is settled before ADR-0003's middleware replaces it, and it must be removed in the same change that lands real authentication. The submitter half of the gate stays deferred (no submitter is recorded to compare against); each gated handler carries a `// deferred` comment.

## Amendment (issue #3): auth landed, submitter half still deferred

ADR-0003 is implemented. The `x-user-id` / `x-user-role` stand-in is **deleted**; `Option<UserClaims>` is now populated from the access JWT by the global auth middleware. What each gate enforces now:

- **Role half, enforced.** `POST /books` -> any signed-in role (`Reader` and up). `PUT /books/{id}/visibility` -> in the handler: a transition whose target is `PendingReview` is open to any signed-in user (the domain guard still refuses `PendingReview` from any state but `Draft`, and a `PendingReview -> PendingReview` self-move is inert), every other target requires `Moderator`/`Admin`. `GET /books?visibility=<v>` -> the override is `Moderator`/`Admin` only; the bare list stays public and defaults to `Listed`. Content-write routes (`creators`, book/cover writes, `chapters`, `releases`) -> `require_roles([Uploader, Moderator, Admin])` route layers; `DELETE` of a creator or book -> `[Moderator, Admin]`. `POST /feedbacks` stays anonymous; the other `feedbacks` routes -> `[Moderator, Admin]`.
- **Submitter half, still deferred.** `books` records no `submitted_by` and `chapter_pages` no `uploaded_by`, so "only the submitter sends their own `Draft` for review", "the submitter edits their own `Draft`", "the submitter reads their own non-`Listed` book and its content", and "staged pages scoped to the calling uploader" are not enforced. The `// deferred` comments at those handlers are narrowed to name only the submitter-scoped behavior. The content gate's identity-free half (moderator-or-above reads any state) is enforced via `UserClaims::can_moderate`.

**Schema.** `books` gains `visibility text not null` (no column `default`; the initial `Draft` is written by the insert statement itself, per `docs/sql.md`) and `submitted_at timestamptz null` (a review queue ordered by wait time needs it -- the queue keeps the ordinary `id`-descending cursor and merely exposes `submittedAt` as a field). It does **not** gain `published_at` or `hidden_at` -- reconstructable from an audit log once auth brings one. Nothing is deployed, so the columns join the original `books` migration rather than an alter-and-backfill. The list scan is supported by a composite `books(visibility, id)` index rather than a partial one on `where visibility = 'Listed'`: the filter is a bind parameter, so a partial index only helps when the planner can prove the parameter equals the predicate's literal, which a generic plan cannot. The composite serves the default `Listed` scan and the `?visibility=` override alike, as an index-only scan whose ordering matches the cursor.

Because every write and every page read must know the owning `Book`'s state, `chapter_releases` and `chapter_pages` each carry their own `book_id`, denormalized from their parent. Without it the lookup behind a release write is a two-table walk and the one behind a page read a three-table walk; with it every one is a single join. The column is never client-supplied -- each insert derives it from its parent row in the same statement -- so it cannot drift. Its FK to `books` is `on delete restrict` too, so a surviving release or page blocks `DELETE /books/{id}` directly, alongside the chapter-mediated route ADR-0006 describes.

**The hide-request channel** is the separate `Feedback` entity, shipped in its own issue (submitted by a `Guest` or `User`, no `Role` required; `kind` one of `Report`/`Correction`/`General`; `status` one of `Open`/`Resolved`/`Dismissed`; optional `book_id` FK, `ON DELETE SET NULL` but non-null-required at `POST /feedbacks` for book-bound kinds). It has no foreign key back into the visibility machine -- a moderator reads a `Report` and calls `PUT /books/{id}/visibility` themselves, and that transition's `note` carries the reason.
