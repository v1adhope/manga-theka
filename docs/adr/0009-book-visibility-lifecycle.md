# Book visibility is a five-state moderation lifecycle, separate from Book Status, shipped before auth as a state machine only

A `Book` gains a `visibility` axis -- `Draft`, `PendingReview`, `Listed`, `Rejected`, `Hidden` -- as a `CHECK`-constrained `text` column on `books` per `docs/sql.md`'s closed-set convention, entirely separate from `books.status`. `Book Status` (`Ongoing`/`Completed`/`Hiatus`/`Cancelled`) describes the work's progress; `CONTEXT.md` already scopes it to exclude "the catalog record's moderation or visibility state", and "published" was unavailable since ADR-0006 spends it on a `Chapter Release` published-by-having-a-committed-page. Merging the two would overload a four-value set meaning something orthogonal, so visibility gets its own column, `CONTEXT.md` term, and endpoint. `Book Status` is untouched.

Every `Book` is created `Draft`, and `POST /books` is open to any signed-in user (`Reader` and up), not just `Uploader` -- proposing a title is a personal action, publishing it is not. The only transition a submitter may make is `Draft -> PendingReview`; once submitted they can't pull it back, so a moderator always reviews a state the submitter can't mutate underneath them. Every other transition is a moderator action, all through one endpoint, `PUT /books/{id}/visibility` with `{ target, note? }`, guarded by a fixed table: `Draft -> {PendingReview, Rejected, Hidden}`, `PendingReview -> {Listed, Draft, Rejected}`, `Listed -> {Hidden, Rejected}`, `Hidden -> {Listed, Draft, Rejected}`, `Rejected` terminal. An illegal cell is `409` (the conflict-with-current-state reading ADR-0002 and ADR-0006 already apply); an unknown enum value is `422`. This is the opposite of ADR-0006's per-verb RPC choice for release `commit`/`upload`, deliberately so: those are steps in an upload session, this is a single state transition whose target the client names, so a guard table beats six near-identical handlers.

`Rejected` is a moderator-set dead end -- a deferred sweeper reclaims rejected books and their media later, tracked as a future issue, not built now. `PendingReview` and `Rejected` both freeze the book: `PUT /books/{id}` and every create/update/delete on its chapters, covers, releases, and pages answer `409` in either state, so review sees a stable snapshot and a rejected book stops changing before the sweeper reaches it. `Hidden` stays writable -- an uploader can fix the reported problem in place, then a moderator moves it back to `Listed` (or `Draft`, or `Rejected`).

The whole feature ships before authentication exists: ADR-0003 designed auth on paper but it was never implemented, `books` has no `uploaded_by`, and issue 1 shipped the catalog deliberately auth-free. Enforcement here is a `// deferred: gate to <role>` comment at each handler naming the role that will guard it, nothing more; there are no `*_by` columns. The consequence, explicit and the same one ADR-0006 accepted for uncommitted releases: a non-`Listed` book is *unlisted, not secret*. `GET /books/{id}` and the by-id chapter/release/page routes still serve a `Draft`, `PendingReview`, `Rejected`, or `Hidden` book to anyone with the id -- only the `GET /books` list filters, to `Listed` by default with `?visibility=<value>` overriding it for the moderator queue. The identity-free half of the design -- the legal-transition guard, the `PendingReview`/`Rejected` write freeze -- is enforced now; the half needing identity -- who may call which transition, restricting non-`Listed` reads to submitter or moderator, "only the submitter edits their own `Draft`" -- rides with issue 3. Blocking on auth was rejected: the state model and list filtering are independently useful, and the secrecy gap closes exactly when ADR-0006's equivalent gap does.

This consciously diverges from ADR-0006's "no publish flag, no endpoint, no timestamp" stance, because books aren't releases. A release's published state is *derivable* -- at least one committed page, or not -- so a flag would duplicate a fact the pages already carry. "A human approved this book for the public catalog" is derivable from nothing, so it has to be stored. `books` gains `visibility text not null` (no column `default`; `Draft` initial value set in code per `docs/sql.md`), and `submitted_at timestamptz null`, since a review queue ordered by wait time needs it. It does **not** gain `published_at` or `hidden_at`: reconstructable from an audit log once auth brings one, and adding them now is storage for a question nobody can ask yet. Existing rows backfill to `Listed`; a partial index `where visibility = 'Listed'` supports the default list scan.

Moderator-to-submitter communication is a single nullable `note text` on `books`, capped at 2000 characters (matching `Description`, via a `Note` newtype rejecting empty-or-whitespace) with a `check_length_books_note` backstop. It's submitter-visible; deliberately no second staff-only field, since without auth nothing could keep one private and a speculative split isn't worth the column. `note` is written by code on `Draft -> PendingReview` (fixed "submitted, please be patient" message), required and non-empty on any transition into `Rejected` or `Hidden` and on the return `-> Draft` (`422` if missing), and cleared on `-> Listed` and `Hidden -> Listed` unless the caller supplies a replacement. `PUT /books/{id}/note` sets or clears it without a transition, for an already-`Listed` book. A `book_review_notes` history table was rejected -- one overwritten field is enough until there's an audit log to hang history on. Two booleans (`is_draft`+`is_hidden`) instead of one enum were rejected for v1: the actor-and-reason distinction they'd preserve isn't recorded anywhere without an audit trail, and a single closed enum matches how `kind`/`status` are already modeled on this table -- revisit when auth lands.

The "someone requested the hide" channel is a separate `Feedback` entity in its own issue (submitted by a `Guest` or `User`, no `Role` required; `kind` one of `Report`/`Correction`/`General`; `status` one of `Open`/`Resolved`/`Dismissed`; optional `book_id` FK, `ON DELETE SET NULL` but non-null-required at `POST /feedback` for book-bound kinds). It has no foreign key back into the visibility machine -- a moderator reads a `Report` and calls `PUT /books/{id}/visibility` themselves; until it exists, the `hide` transition's `note` carries the reason.
