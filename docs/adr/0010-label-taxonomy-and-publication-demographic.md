# Labels become a three-kind curated taxonomy, and publication demographic moves onto books

`labels.kind` grows from `Genre`/`Tag` to `Genre`/`Theme`/`Presentation`, and the seed grows from 31 sample rows to 70 curated ones -- 27 `Genre`, 38 `Theme`, 5 `Presentation`. The six existing `Tag` rows (`Mafia`, `Music`, `School Life`, `Survival`, `Time Travel`, `Zombies`) are all themes: they keep their ids with `kind` rewritten; the 25 existing genres are untouched. `Tag` disappears as a kind because it never named an axis, only "not a `Genre`" -- a catalog that cannot say whether `Long Strip` describes a subject or a shape pushes that distinction into every client's picker. Nothing is deployed, so this edits the original `20260629101118_add_labels` migration in place (keeping the `on conflict(name) do update` shape so a re-run stays idempotent), not a second seed migration.

**The third kind is `Presentation`, not `Format`**, because `CONTEXT.md` defines `Book Kind` as "the publication format" and lists `Format` under its `_Avoid_` -- naming the kind `Format` would reintroduce the banned word and leave two terms competing. `Presentation` is deliberately broad (how a `Book` is packaged *or* where it came from) and holds five values: `Long Strip`, `Full Color`, `Oneshot`, `Adaptation`, `Self-Published`. The first three are load-bearing -- a long-strip webtoon is a different reading experience from a paged book, `Full Color` is a property of the original manhwa work rather than of any one upload, and `Oneshot` answers "something I can finish tonight" -- and no other column in the schema captures them. `Adaptation` and `Self-Published` are provenance rather than packaging; a fourth kind for two values would cost a `CHECK` value, an API concept, and a UI section, so the broad definition absorbs them. Caveat for whoever reads this next: if a reader client ever needs `Long Strip` to *choose a rendering mode* rather than to filter, that is a `books` column, not a label (a label is something you search by, not something you branch layout on), and it would arrive as an additive migration without disturbing this kind.

**Seven values were added on top of the base vocabulary**, because that vocabulary is Japan-centric while `Book Kind` commits this catalog to Manhwa and Manhua. `Xianxia` and `Murim` join `Genre`: `Wuxia` was the only Chinese-native genre present and covers neither cultivation fantasy (no immortals, no cultivation) nor the Korean martial world, both large categories here. `Regression`, `Dungeons`, `Game System`, `Revenge`, and `Super Powers` join `Theme`, each because an existing value looked like it covered the ground and does not: `Regression` (dying and returning to one's own past) is neither `Time Travel` nor `Reincarnation`; `Dungeons` is not `Isekai`, since the protagonist never leaves their world; `Game System` (game mechanics that are literally real) is neither `Video Games` (playing one) nor `Virtual Reality` (being inside one); `Super Powers` covers powers without the Western `Superhero` idiom; and `Revenge`, a dominant driver in this catalog's material, had no representation. `Traditional Games` was renamed `Strategy Games` -- accurate for go, shogi, and karuta but close to meaningless to an English reader; the rename widens the sense to chess and card games, the cheaper error.

**Eight base-vocabulary values were rejected**, in four groups:

- `Loli`, `Shota`, `Incest` -- a content-policy decision: in several jurisdictions the first two name material illegal to host regardless of labeling, and a curated label shapes what gets submitted *before* `Book Visibility` review ever sees it, so that flow is not the answer here.
- `Fan Colored`, `Official Colored` -- wrong entity: colorization is a property of one scanlation group's upload (a `Chapter Release`), and tagging the whole `Book` becomes false the moment a second, uncolored release exists. `Full Color` survives that test because for manhwa it describes the original work.
- `Award Winning` -- unverifiable and unmaintainable (which award, which year, adjudicated by whom) and, with no label CRUD, uncorrectable.
- `User Created` -- specific to another platform's model. `Gyaru` -- opaque to an English-first audience, and a character type rather than a theme.

*Rejected: a fourth kind for content warnings (`Gore`, `Sexual Violence`). `Content Rating` is already the audience-suitability signal, exactly one per `Book`, and a second overlapping axis invites the two to disagree. The consequence is recorded deliberately because it gets reopened without context: a reader cannot filter *out* graphic content while still reading `Mature` titles, since the only lever is the rating itself. If that matters, the answer is a fourth `Label Kind`, not folding warnings into `Theme` where "exclude gore" would be indistinguishable from "exclude cooking".*

*Rejected: a `code`/slug column on `labels`. Tempting because `content_ratings` and `languages` both carry one, and it would make a filter query string readable and greppable. Rejected because labels stay read-only and migration-seeded, and issue 1 already established that a client fetches `GET /labels` to build a picker before filtering -- so nothing is blocked by ids, and a second identifier would be a second thing to keep unique and stable. Accepted consequence: filter query strings are UUID soup and any investigation of a filter bug begins with `GET /labels`. `labels.id` stays the only identifier, in requests and responses alike.*

**There is no label CRUD and no `retired_at`**, both deferred to the enum-CRUD issue that issue 1 already promised. They belong together: with no write endpoint nothing can retire a label, and `book_labels.label_id` is `on delete restrict`, so a label any `Book` references cannot be deleted regardless. Whoever builds that endpoint owns retirement, and should reach for a `retired_at timestamptz` that hides a label from pickers and filters while leaving existing attachments intact, rather than a delete the FK will refuse.

**`books` gains `publication_demographic`** -- a `not null` `text` column constrained by `enum_books_publication_demographic` to `Shounen`, `Shoujo`, `Seinen`, `Josei`, or `Kids`, joining the original `20260629100955_add_books` migration in place. It is a column rather than a fourth `Label Kind` because it is a closed set with exactly one value per `Book`, and a label cannot enforce that cardinality -- the same reasoning ADR-0004 used to collapse `kind` and `status` into `CHECK` constraints. It is mandatory, joining `kind`, `status`, `content_rating_id`, and `publication_language_id`, so the `GET /books` facet partitions the whole catalog instead of leaving a remainder that matches no value a reader can pick. *Rejected: a nullable column, and an `Unknown` member -- each reintroduces a sixth, non-answer state, differing only in whether it is spelled as NULL or as a string.* Since `docs/sql.md` bans column defaults, the value is supplied by code on every insert. Accepted cost: a work whose original publisher marketed to no demographic (self-published manhwa most of all) carries a best-fit judgement rather than a recorded fact; correcting one is an ordinary metadata edit on a `Listed` `Book`, and `Feedback` of kind `Correction` is the dispute channel. `Kids` is included -- real for manga, harmless for manhwa.

*Rejected: folding demographic into `Content Rating`. The two look interchangeable and are not -- `Content Rating` describes what is in a book, demographic describes the readership its original publisher marketed it to. The mapping is many-to-many in both directions (a `Seinen` work can be rated `Everyone`, a `Shounen` work `Mature`), so collapsing them means a reader filtering `Mature` to find seinen gets shounen back. This makes `Book Kind`'s `_Avoid_: Demographic` line guard against a real neighbouring term rather than a hypothetical one.*
